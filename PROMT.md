# CoreLink.Foundation — архитектурный промт v3

**Репозиторий:** https://github.com/Bodden007/CoreLink.Foundation  
**Ветка:** `main`  
**Стек:** C# / .NET 10 / NativeAOT / NModbus 3.0.83  
**Статус:** архитектура частично реализована, дальнейшие изменения проходят ручное утверждение.

## 1. Основная архитектура

CoreLink использует два независимых контура:

- **Core Polling** — непрерывный обмен с PLC через существующий Modbus Transport.
- **Client / Rx** — периодическое получение согласованного snapshot и публикация значений.

Core Polling не зависит от скорости Client / Rx.

**CoreLink.Client — единственная публичная точка управления системой.**

Маршрут данных:

PLC → Transport → Core → Client → Rx → HMI

Маршрут команд:

HMI → Client → Core → Transport → PLC

## 2. Ответственность компонентов

### CoreLink.Core

- Управляет `ModbusTransportSession`.
- Хранит последний согласованный декодированный snapshot.
- Выполняет собственный polling через существующий Transport.
- Предоставляет синхронный `GetSnapshot(float*, int)`.
- Не владеет клиентским массивом и не сохраняет указатель.
- Предоставляет Read / Write через существующий Dispatcher.
- Передаёт состояние ядра через `StatusChanged`.
- Не зависит от Rx и HMI.

### CoreLink.Client

- Загружает бинарную карту.
- Создаёт единственный `float[]` на сессию.
- Управляет Core и Rx.
- Запрашивает snapshot каждые 500 мс.
- Временно закрепляет массив через `fixed`.
- Передаёт массив Rx только после успешного заполнения.
- Ожидает `Ready` перед следующим заполнением.
- Не накапливает пропущенные циклы.
- Управляет синхронными `Start()` / `Stop()`.

### CoreLink.Rx

- Синхронно обрабатывает `ReadOnlySpan<float>`.
- Не изменяет и не сохраняет исходный массив.
- Не работает с указателями.
- Публикует подписчикам отдельные значения.
- Возвращает `Ready` после завершения обработки.
- Не влияет на Core Polling.

## 3. Контракт памяти

- Client создаёт и владеет единственным `float[]`.
- Core получает временное право записи только на время `GetSnapshot()`.
- Pinning существует исключительно внутри `fixed`.
- Указатель не сохраняется и не используется после возврата из вызова.
- При неуспешном `GetSnapshot()` клиентский массив не изменяется.
- Rx не получает указатель и не сохраняет исходный массив.
- Повторное заполнение допускается только после `Ready`.

Дополнительные копирования Client → Rx не вводить.

## 4. Бинарная карта v2

**Утверждена только версия 2. Поддержка v1 исключена.**

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | Version |
| 1 | 2 | TotalLength |
| 3 | 4 | IPv4 |
| 7 | 2 | Port |
| 9 | 1 | UnitId |
| 10 | 4 | PollIntervalMs |
| 14 | 4 | ConnectTimeoutMs |
| 18 | 4 | RequestTimeoutMs |
| 22 | 4 | ReconnectDelayMs |
| 26 | 2 | StartAddress |
| 28 | 2 | RegisterLength |
| 30 | 1 | RegisterOrder |
| 31 | 2 | ValueCount |
| 33+ | 3 × N | Registers |

**Размер:** `33 + ValueCount × 3`.

- Числовые поля — Little Endian.
- Запись регистра — `UInt16 Address + byte Type`.
- Неизвестная версия отклоняется как некорректная конфигурация.
- Три таймаута обязательно поступают из карты, а не задаются в Core константами.
- Transport не изменять.

Изменения v2 подготовлены в `CoreMapLayout`, `CoreLinkMap`, `CoreMapEncoder`, `TransportMap`, `CoreMapDecoder`. Для Decoder добавлена проектная зависимость от Contracts.

Последний предоставленный результат `dotnet build`: **сборка успешна, 0 ошибок, 1 предупреждение CS0067**.

Проверка выполнения Encoder → Decoder отдельно ещё не подтверждена.

## 5. Lifecycle Core

### Start(CoreMap)

1. Проверяет бинарную карту v2.
2. Создаёт конфигурацию Transport из карты.
3. Создаёт `ModbusTransportSession`.
4. Запускает Transport.
5. Возвращает `CoreStatus.Running` после успешного запуска Transport.

**Подключения PLC ожидать не требуется.**

PLC может быть недоступен в момент запуска. За подключение и штатный reconnect отвечает Transport.

### Stop()

`Stop()` строго синхронный.

1. Прекращает новые операции Core.
2. Останавливает polling.
3. Ожидает завершения активных Modbus-операций, включая обработку timeout.
4. Завершает Dispatcher.
5. Освобождает ресурсы Transport.
6. Уничтожает внутренний snapshot.
7. Возвращает состояние `Stopped`.

После возврата из `Stop()` активных операций Transport не остаётся.

Повторный `Stop()` не должен приводить к ошибке.

Повторный `Start()` на том же экземпляре после остановки пока не реализовывать. Восстановление Core после внутренних сбоев будет проектироваться отдельно от штатного TCP reconnect.

## 6. Статусы и сохранение данных

**Состояние Core и результат GetSnapshot — разные контракты.**

- `StatusChanged` сообщает о состоянии ядра.
- `GetSnapshot()` отвечает за получение согласованных значений.
- Rx не определяет состояние соединения по значениям регистров.

### До первого успешного чтения

- Core уже может быть запущен.
- Данных ещё нет.
- `GetSnapshot()` возвращает `SnapshotStatus.NoData`.
- Клиентский массив не изменяется.
- Polling продолжает работу.

### Потеря связи после успешного чтения

**Утверждённое поведение:**

1. Core сохраняет последний согласованный snapshot.
2. Последние действительные значения остаются на HMI.
3. HMI показывает отдельный статус **No Data**.
4. Устаревшие значения не выдаются за новые измерения.
5. Transport продолжает reconnect.
6. После успешного восстановления чтения значения обновляются, статус No Data снимается.

Client и Rx не должны самостоятельно определять потерю связи по содержимому массива. Используется отдельный канал состояния Core.

Точная семантика результата `GetSnapshot()` при наличии сохранённых данных и потере соединения не должна изменяться без отдельного согласования.

### После Stop

- Внутренний snapshot уничтожен.
- `GetSnapshot()` возвращает `SnapshotStatus.Stopped`.
- Клиентский массив не изменяется.
- Старые данные через Core больше не выдаются.

## 7. Согласованность snapshot

При успешном polling:

1. Transport получает регистры.
2. Core декодирует данные по карте.
3. Полный результат согласованно публикуется во внутреннее состояние.
4. `GetSnapshot()` копирует только завершённый snapshot.

Недопустимо смешивать данные разных циклов polling.

Синхронизация внутреннего snapshot не удерживает блокировку во время сетевого Modbus-запроса.

Конкретный механизм синхронизации утверждается отдельно.

## 8. Read / Write

Маршрут:

Client → Core → ModbusTransportSession → Dispatcher → PLC

Приоритеты сохраняются:

**Write → Polling Read → Single Read**

- Используется существующее TCP-соединение.
- Read / Write не управляют snapshot-циклом.
- Не создаются дополнительные TCP-сессии.
- Существующие Dispatcher и Poller не переписывать.
- Ожидаемые ошибки возвращать статусами.

## 9. Текущее состояние разработки

### Реализовано или подготовлено

- `ICore` с `Start(CoreMap)`, синхронным `Stop()` и `GetSnapshot(float*, int)`.
- `SnapshotStatus`.
- Бинарная карта v2.
- Encoder / Decoder v2.
- Три параметра таймаутов в моделях карты.
- Подключение Core к Contracts и Transport на уровне зависимостей.
- Существующий Modbus Transport с polling, Dispatcher и reconnect.

### Ещё не реализовано

- Реальный lifecycle `CoreLinkCore`.
- Создание и запуск `ModbusTransportSession` из Core.
- Декодирование polling-данных во внутренний snapshot Core.
- Согласованная синхронизация snapshot.
- Реализация `GetSnapshot()`.
- Публикация состояний через `StatusChanged`.
- Интеграция Client / Rx с новым snapshot-контрактом.
- Интеграция одиночных Read / Write через Core.

`CoreLinkCore.cs` пока содержит временные заглушки `FIXME`.

Предупреждение `CS0067` связано с неиспользуемым `StatusChanged`.

## 10. Правила разработки

- Перед изменением проверять актуальные файлы GitHub `main`.
- Весь код выдавать непосредственно в чате.
- Строго один файл за шаг, полный код файла.
- Следующий файл только после подтверждения.
- Не писать код без отдельного разрешения.
- Не менять публичные контракты самостоятельно.
- Не вводить лишние интерфейсы, фабрики и архитектурные слои.
- Не использовать runtime reflection.
- NativeAOT-first, KISS, YAGNI.
- Минимальный diff.
- Не переписывать работающие компоненты.
- Ожидаемые эксплуатационные ошибки возвращать статусами.
- Комментарии объясняют назначение и ограничения.
- Временные решения маркировать `FIXME` с условием удаления.
- Не выдумывать API и отсутствующие реализации.
- Не объявлять успешную сборку без реального результата.
- Каждое изменение проходит ручной review пользователя.

## 11. Следующий этап

**Продолжить с `CoreLink.Core/Runtime/CoreLinkCore.cs`.**

Перед написанием кода необходимо проверить фактические контракты `CoreStatus`, `ModbusTransportSession`, `CoreMapDecoder` и текущую реализацию Core.

Утверждённые условия lifecycle не пересматривать без конкретного технического основания.

Начать с анализа оставшихся неизвестных контрактов интеграции Transport и snapshot. Новые архитектурные решения не принимать самостоятельно.

**Финальное правило:** архитектура, публичные контракты и весь код утверждаются пользователем.
