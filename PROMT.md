# CoreLink.Foundation — архитектурный промт v4

**Репозиторий:** https://github.com/Bodden007/CoreLink.Foundation  
**Ветка:** `main`  
**Стек:** C# / .NET 10 / NativeAOT / NModbus 3.0.83  
**Статус:** транспорт реализован, клиентский адаптер подготовлен, Core требует реализации.

## 1. Назначение

CoreLink.Foundation — промышленный фундамент обмена данными между ПЛК и клиентскими приложениями.

Приоритеты:

1. Надёжность.
2. Предсказуемость.
3. Сопровождаемость.
4. Простота.
5. NativeAOT.
6. Производительность.

Архитектура проектируется для продолжительной непрерывной работы в АСУ ТП.

Не создавать абстракции ради абстракций.

### Главный принцип

**Client зависит только от контракта `ICore`, а не от конкретной реализации ядра.**

Адаптеры являются самостоятельными подключаемыми библиотеками.

Выбор реализации выполняет разработчик приложения на этапе компоновки приложения.

Никаких runtime reflection, `Assembly.Load`, `dynamic`, автоматических фабрик или поиска библиотек.

## 3. CoreLink.Client

Client — единственная публичная точка управления системой для внешнего приложения.

Ответственность:

- загрузка карты через `IMapProvider`;
- создание единственного `float[]` на сессию;
- управление жизненным циклом через `ICore`;
- периодическое получение snapshot;
- передача полученных данных Rx;
- управление состоянием Client;
- корректная остановка.

Client получает готовую реализацию `ICore` через конструктор.

Client не должен:

- создавать конкретное ядро;
- знать язык реализации Core;
- обращаться к FFI;
- управлять TCP;
- декодировать Modbus-регистры;
- самостоятельно выполнять reconnect.

**Client не имеет ProjectReference на `CoreLink.Core` или библиотеки адаптеров.**

## 4. Контракт ICore

`ICore` — контракт, определяющий операции, необходимые Client.

Текущий интерфейс:

```csharp
public unsafe interface ICore
{
    CoreStatus Start(CoreMap coreMap);

    CoreStatus Stop();

    SnapshotStatus GetSnapshot(
        float* buffer,
        int length);

    event Action<CoreStatus>? StatusChanged;
}
```

Контракт не определяет внутреннее устройство Core.

Ни C# Core, ни Rust Core не обязаны реализовывать клиентский интерфейс непосредственно.

**`ICore` реализует подключаемый адаптер.**

Сам интерфейс не выбирает реализацию ядра.

## 5. Подключаемые адаптеры

### CoreLink.Adapter.CSharp

Отдельная библиотека .NET 10.

Зависимости:

- CoreLink.Contracts;
- CoreLink.Core.

Адаптер:

- реализует `ICore`;
- создаёт C# Core;
- вызывает его методы напрямую;
- передаёт результаты и события Client;
- не выполняет polling;
- не декодирует значения;
- не хранит snapshot.

### CoreLink.Adapter.Rust — перспектива

Отдельная библиотека, реализующая тот же `ICore`.

Связь с Rust осуществляется через C ABI / FFI.

Требования:

- стабильные ABI-совместимые типы;
- явные правила ownership;
- явный lifetime;
- детерминированные статусы;
- отсутствие panic через FFI;
- отсутствие хранения клиентского указателя после возврата вызова.

**Единый бинарный ABI между C# Core и Rust Core не требуется.**

Общими являются семантика операций и клиентский интерфейс.

### Правило зависимостей

Адаптер имеет право напрямую зависеть от конкретного ядра.

Это его назначение.

Не создавать дополнительные интерфейсы и проекты исключительно для устранения этой зависимости.

## 6. CoreLink.Core

`CoreLinkCore` — самостоятельная C#-реализация ядра.

Не наследуется от `ICore` и не реализует этот интерфейс.

Ответственность:

- получение и проверка конфигурации;
- создание и управление Modbus Transport;
- непрерывный polling;
- декодирование полученных регистров;
- хранение последнего согласованного snapshot;
- передача snapshot по синхронному запросу;
- публикация состояний;
- выполнение Read / Write через Transport.

Core не знает:

- Client;
- Rx;
- Avalonia;
- конкретные ViewModel;
- клиентские адаптеры;
- способ отображения данных.

## 7. CoreLink.Transport

Существующий Modbus Transport сохраняется.

Используются:

- `ModbusTransportSession`;
- `ModbusConnectionManager`;
- `ModbusRequestDispatcher`;
- `ModbusPoller`;
- `ModbusConnectionConfig`.

Transport отвечает за:

- TCP connection;
- Modbus-запросы;
- таймауты;
- reconnect;
- сериализацию запросов;
- приоритеты Read / Write;
- выдачу исходных регистров и статусов.

Transport не знает Client, Rx или HMI.

### Приоритет запросов

**Write → Polling Read → Single Read**

Использовать существующую TCP-сессию.

Не создавать дополнительные TCP-соединения для UI-команд.

Существующие Dispatcher и Poller не переписывать без конкретной технической причины.

### Второй протокол

OPC UA пока не реализовывать.

Не вводить заранее универсальные транспортные интерфейсы, фабрики или протокольные адаптеры.

Необходимость общей транспортной абстракции определяется после появления второго реального протокола.

## 8. Два независимых цикла

### Core Polling

```text
PLC
 |
 v
Modbus Transport
 |
 v
Raw Registers
 |
 v
Core Decoder
 |
 v
Internal Snapshot
```

Polling работает постоянно и независимо от Client / Rx.

Не накапливает устаревшие запросы.

### Client / Rx

```text
Client Timer
     |
     v
ICore.GetSnapshot()
     |
     v
Client float[]
     |
     v
CoreLink.Rx
     |
     v
HMI
```

Client запрашивает snapshot каждые 500 мс согласно текущему контракту.

Если предыдущая обработка ещё не завершена, новый цикл не запускается.

Очередь пропущенных циклов не создаётся.

## 9. Контракт памяти

Утверждённые правила:

1. Client создаёт и владеет `float[]`.
2. На одну сессию создаётся один клиентский массив.
3. Core хранит собственный внутренний snapshot.
4. Client временно закрепляет массив через `fixed`.
5. `GetSnapshot(float*, int)` выполняется синхронно.
6. Указатель действителен только в пределах вызова.
7. Core не сохраняет указатель.
8. При неуспешном вызове клиентский массив не изменяется.
9. Rx не работает с указателями.
10. Rx не изменяет и не сохраняет исходный клиентский массив.

Дополнительное копирование Client → Rx не вводить.

## 10. Бинарная карта v2

Поддерживается исключительно версия 2.

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | Version |
| 1 | 2 | TotalLength |
| 3 | 4 | IPv4 |
| 7 | 2 | Port |
| 9 | 1 | UnitId |
| 10 | 4 | PollIntervalMs |
| 14 | 4 | ConnectTimeoutMs |
| 18 | 4 | RequestTimeoutMs |
| 22 | 4 | ReconnectDelayMs |
| 26 | 2 | StartAddress |
| 28 | 2 | RegisterLength |
| 30 | 1 | RegisterOrder |
| 31 | 2 | ValueCount |
| 33+ | 3 × N | Registers |

Размер:

`33 + ValueCount × 3`

Числовые поля — Little Endian.

Регистр:

`UInt16 Address + byte Type`

Неизвестные версии и некорректные размеры отклоняются.

Таймауты и параметры polling поступают из карты.

### Граница декодирования конфигурации

В существующей реализации `CoreMapDecoder` и `TransportMap` находятся внутри проекта Transport и имеют `internal`-доступность.

Способ передачи декодированной конфигурации из Core в Transport пока отдельно не утверждён.

Не изменять доступность классов или публичный API транспорта без согласования.

## 11. Lifecycle Core

### Start(CoreMap)

Утверждённая последовательность:

1. Проверка бинарной карты.
2. Подготовка конфигурации Transport.
3. Создание `ModbusTransportSession`.
4. Запуск Transport.
5. Запуск Core runtime.
6. Возврат `CoreStatus.Running`.

**Успешный Start не требует установленного соединения с PLC.**

Отсутствие PLC — штатное эксплуатационное состояние.

Reconnect выполняется внутри Transport.

### Stop()

Строго синхронный метод.

1. Прекращает новые операции.
2. Останавливает polling.
3. Дожидается активных Modbus-операций.
4. Завершает Dispatcher.
5. Освобождает Transport.
6. Уничтожает внутренний snapshot.
7. Возвращает `Stopped`.

После возврата из Stop активных операций Transport быть не должно.

Повторный Stop безопасен.

Повторный Start на том же экземпляре после Stop пока не реализовывать.

## 12. Snapshot и состояния

### До первого успешного polling

- Core может находиться в Running.
- Данных ещё нет.
- `GetSnapshot()` возвращает `NoData`.
- Клиентский массив остаётся без изменений.

### После успешного polling

Core публикует полностью декодированный согласованный snapshot.

`GetSnapshot()` копирует только завершённое состояние.

Недопустимо смешивать значения разных циклов.

### При потере связи

- Core сохраняет последний согласованный snapshot.
- HMI сохраняет последнее значение.
- HMI отдельно показывает No Data.
- Устаревшие значения не считаются свежими.
- Transport выполняет reconnect.
- После восстановления успешный polling обновляет значения.

Состояние соединения не определять по значениям регистров.

**Точная семантика `GetSnapshot()` при наличии старых данных и потере связи пока требует отдельного согласования.**

### После Stop

- Snapshot уничтожен.
- `GetSnapshot()` возвращает `Stopped`.
- Клиентский массив не изменяется.

## 13. Синхронизация

Принципы:

- один логический владелец Transport;
- отсутствие параллельных Modbus-запросов через одну сессию;
- согласованная публикация snapshot;
- отсутствие длительного удержания блокировки snapshot во время сетевого запроса;
- отсутствие неограниченных очередей;
- отсутствие бесконтрольных фоновых задач.

Механизм синхронизации внутреннего snapshot будет согласован перед реализацией.

Не применять lock-free без подтверждённой необходимости.

## 14. NativeAOT

NativeAOT — обязательное требование.

Запрещено использовать без отдельного согласования:

- runtime reflection;
- `dynamic`;
- `Assembly.Load`;
- `Reflection.Emit`;
- автоматическое обнаружение реализаций;
- DI-контейнеры, зависящие от runtime scanning.

Адаптеры подключаются явно.

`IsAotCompatible=true` не заменяет проверки NativeAOT publish конечного приложения.

NModbus 3.0.83 ранее прошёл отдельную NativeAOT-проверку.

## 15. Правила разработки

- Код выдаётся непосредственно в чате.
- Один файл за шаг, если пользователь не разрешил пакетное изменение.
- Полный код файла.
- Имена и расположение новых файлов согласуются.
- Не переписывать рабочий компонент без необходимости.
- Не менять архитектуру самостоятельно.
- Не изменять публичные контракты без согласования.
- Минимальный diff.
- KISS / YAGNI / NativeAOT-first.
- Ожидаемые эксплуатационные ошибки возвращать статусами.
- Не маскировать программные ошибки состоянием PLC offline.
- Не добавлять зависимости без необходимости.
- Комментарии объясняют назначение и ограничения.
- Временный код помечается FIXME с условием удаления.
- При изменении API сразу проверять связанные вызовы и зависимости.
- Не оставлять неиспользуемые типы и устаревшие зависимости.
- Сборку считать успешной только после фактической проверки.
- Код и архитектуру окончательно утверждает пользователь.

Проверка этапа:

   v

   v

## 16. Последнее подтверждённое состояние

`CS0067: CoreLinkCore.StatusChanged никогда не используется`

Причина: lifecycle Core пока содержит заглушки.

### Подготовлено локально

- `CoreLinkCore` больше не реализует `ICore`.
- Удалён механизм выбора `CoreBackend`.
- Создан `CoreLink.Adapter.CSharp`.
- `CSharpCoreAdapter` реализует `ICore`.
- Client принимает `ICore` через конструктор.
- Удалена прямая проектная зависимость Client от C# Core.
- Исправлены смещения диагностических проверок карты v2.
- Добавлен адаптер в solution.

Последняя подтверждённая сборка включает семь проектов.

**Важно:** локальные изменения ещё не подтверждены как опубликованные в GitHub. Перед дальнейшей работой проверять актуальную версию репозитория и учитывать это различие.

### Что пока не реализовано

- Реальный lifecycle Core.
- Создание Transport из Core.
- Декодирование polling-данных в snapshot.
- Синхронизация snapshot.
- Работающий GetSnapshot.
- Публикация StatusChanged.
- Интеграция Rx.
- Вызовы одиночных Read / Write через Core.
- Rust Core и Rust Adapter.

Цель — подключить существующий `ModbusTransportSession` к ядру.

Перед генерацией кода:

1. Проверить актуальные исходники Core и Transport.
2. Установить, как Core получает декодированную конфигурацию карты.

5. Определить недостающие контракты snapshot и состояния.

Не переписывать Transport.

Не создавать дополнительные архитектурные слои.

Не начинать Rust и OPC UA.

После согласования необходимых границ реализовывать Core небольшими проверяемыми шагами.
