# CoreLink.Foundation — архитектурный промт v6

**Репозиторий:** https://github.com/Bodden007/CoreLink.Foundation  
**Ветка:** `main`  
**Стек:** C# / .NET 10 / NativeAOT / NModbus 3.0.83  
**Состояние документа:** актуализировано по GitHub `main` и испытаниям 09.11.2026. Текущий этап: завершение Client и подключение `ICore`.
**Последняя проверка:** успешный Release Rebuild CoreSimulator и зависимостей; подтверждён обмен с внешним PLC Simulator, reconnect и остановка во время зависшего запроса. Полная NativeAOT-публикация не подтверждена.

## 1. Назначение и приоритеты

CoreLink.Foundation — фундамент обмена данными между ПЛК и клиентскими приложениями для промышленного ПО.

Приоритеты в порядке важности: **надёжность → предсказуемость → сопровождаемость → простота → NativeAOT → производительность**.

Предпочитать минимальную проверяемую реализацию. Не создавать абстракции и поддержку гипотетических сценариев заранее.

## 2. Утверждённая архитектура

```text
                   Avalonia HMI
                        |
                        v
                 CoreLink.Client
                        |
                       ICore
                        ^
                        |
             Подключаемый адаптер
                  /           \
                 v             v
   CoreLink.Adapter.CSharp  CoreLink.Adapter.Rust
                 |          (не реализован)
                 v             |
           CoreLink.Core    Rust Core
                 |          (перспектива)
                 v
          CoreLink.Transport
                 |
             Modbus TCP
                 |
                PLC
```

**Client зависит от `ICore`, не от конкретного ядра.** C#-адаптер реализует `ICore` и вызывает C# Core напрямую. Rust-адаптер — возможная будущая реализация; сейчас его нет.

Реализацию адаптера выбирает разработчик приложения явно при компоновке. Нет runtime reflection, `Assembly.Load`, автоматического поиска реализаций и DI-контейнеров для этой задачи.

`CoreLink.Core` не реализует `ICore` непосредственно. Это ответственность адаптера.

| `CoreLink.Transport` | Modbus TCP, непрерывный polling, reconnect, timeout, последовательность запросов, приоритет Read/Write, исходные `ushort[]` |

Не переносить Modbus-адреса, сетевую логику и детали транспорта в UI, Rx или Client.

### Ответственность Core и Transport — утверждено

- **Core декодирует бинарную карту**, хранит определения регистров, преобразует полученные `ushort[]` в значения и владеет `ModbusTransportSession`.
- **Transport не декодирует бинарную карту и не работает с клиентскими указателями.** Он получает готовый `ModbusConnectionConfig`, выполняет постоянный опрос и Modbus-операции.
- **Приоритеты одиночного чтения и записи остаются в Transport**, в существующем `ModbusRequestDispatcher`. Команды и результаты проходят через Core; второй диспетчер в Core не создавать.
- Старые типы декодирования карты в Transport могли сохраниться для диагностики; наличие устаревшего кода проверять отдельно, не считать его утверждённой архитектурной границей.

## 4. Контракт ICore

Текущий контракт:

```csharp
public unsafe interface ICore
{
    CoreStatus Start(CoreMap coreMap);
    CoreStatus Stop();
    SnapshotStatus GetSnapshot(float* buffer, int length);
    event Action<CoreStatus>? StatusChanged;
}
```

`ICore` реализует `CoreLink.Adapter.CSharp`, а не непосредственно `CoreLinkCore`. Клиент получает адаптер через конструктор.

**Не добавлять `Read`/`Write` в `ICore` без отдельного утверждения API.** Концептуально эти операции проходят `Client → Core → Transport`, но публичные сигнатуры ещё не согласованы.

## 5. Два независимых цикла данных

### Непрерывный polling

```text
PLC → Transport Polling → ushort[] → Core Decode → Internal Snapshot
```

- Polling стартует вместе с Transport.
- **`PollIntervalMs` задаётся бинарной картой**, а не фиксированной константой Core или TestHost.
- Следующий запрос не создаётся до завершения предыдущего; очередь устаревших polling-запросов не накапливается.
- Потеря ПЛК не останавливает приложение; reconnect выполняет Transport.

### Запрос Client / Rx

```text
Client periodic request → ICore.GetSnapshot(pointer, length)
                       → копирование готового Core snapshot
                       → Client float[] → Rx → HMI
```

- Текущий предусмотренный интервал получения snapshot со стороны Client/Rx — 500 мс; не путать с `PollIntervalMs` карты.
- `GetSnapshot()` **не инициирует Modbus-запрос**, не меняет частоту polling и не ждёт сеть.
- Rx не работает с указателями и не управляет Transport.
- В текущем `CoreLink.Client` ещё нет получения snapshot. TestHost вызывает `ICore.GetSnapshot` напрямую через адаптер, а не через Client.

## 6. Контракт памяти и snapshot

1. Client создаёт и владеет одним `float[]` на сессию; его длина равна количеству значений карты.
2. `CoreMap.Buffer` — бинарные байты конфигурации; **`CoreMap.BufferLength` — число выходных значений**, не количество байтов.
3. Client временно закрепляет `float[]` через `fixed` и передаёт `float*` и длину в синхронный `GetSnapshot()`.
4. Указатель действителен только внутри вызова. Core его не сохраняет и не передаёт Transport.
5. Core хранит **собственный** последний согласованный snapshot. Polling формирует целиком новое состояние, затем публикует его.
6. `GetSnapshot()` только копирует готовое состояние; при неуспешном результате клиентский буфер остаётся неизменным.
7. После успешного polling данные становятся актуальными; при потере связи последнее успешное значение сохраняется в Core, но считается stale.
8. HMI должно отличать последнее известное значение от свежих данных и отдельно отображать отсутствие связи.

**Семантика текущего `GetSnapshot()`:** до первой успешной публикации возвращается `NoData`, даже если Core уже перешёл в `Disconnected`; при наличии ранее полученных, но устаревших данных — `Disconnected` без копирования. После остановки — `Stopped`.

Согласованность snapshot решена внутри Core; не возвращаться к выбору механизма синхронизации без обнаруженной конкретной ошибки или изменения требований.

## 7. Бинарная карта v2

Поддерживается только версия 2. Числовые поля — **Little Endian**.

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | Version |
| 1 | 2 | TotalLength |
| 3 | 4 | IPv4 |
| 7 | 2 | Port |
| 9 | 1 | UnitId |
| 10 | 4 | PollIntervalMs |
| 14 | 4 | ConnectTimeoutMs |
| 18 | 4 | RequestTimeoutMs |
| 22 | 4 | ReconnectDelayMs |
| 26 | 2 | StartAddress |
| 28 | 2 | RegisterLength |
| 30 | 1 | RegisterOrder |
| 31 | 2 | ValueCount |
| 33+ | 3 × N | Registers: `UInt16 Address + byte Type` |

Размер: `33 + ValueCount × 3` байт.

Типы значения: `Word`, `Float`. Порядки регистров в общем контракте: `ABCD`, `BADC`, `CDAB`, `DCBA`.

**Нельзя самовольно менять формат, размеры полей, смысл `BufferLength` и нумерацию типов.** Неверные версии, размеры, типы и диапазоны должны отклоняться до запуска.

## 8. Декодирование карты и конфигурация — реализовано

В GitHub уже присутствуют `CoreLink.Core/Configuration/Decoding/CoreMapDecoder.cs`, `Configuration/Models/DecodedCoreMap.cs`, `Configuration/ModbusConfigFactory.cs` и `Runtime/CoreLinkCore.cs`.

Core декодирует бинарную карту v2, валидирует параметры и диапазоны, сохраняет описания `Word`/`Float` и порядок регистров. В Transport передаётся только готовый `ModbusConnectionConfig`, без клиентских буферов и указателей. `CoreLink.Maps` формирует карту. Никакой новой фабрики или второго диспетчера в Core не создавать.

Конкретные timeout и интервалы выбираются картой. **10 секунд** в недавних испытаниях — тестовое значение `RequestTimeoutMs`, не норматив для эксплуатации. Текущий Core валидирует `RegisterLength <= 125`; автоматическое разбиение запросов за пределами блока не заявлять реализованным.

## 9. Lifecycle Core — реализован и частично проверен

`CoreLinkCore.Start(CoreMap)` проверяет и декодирует карту, создаёт одну `ModbusTransportSession`, подписывается на события, выделяет собственные буферы декодирования/snapshot и запускает polling. `Running` не означает успешное подключение к PLC.

`CoreLinkCore.Stop()` синхронно завершает Transport, очищает Core snapshot и возвращает `Stopped`. Повторный `Start` на одном экземпляре не предусмотрен.

В испытаниях подтверждены нормальный обмен, восстановление связи, обнаружение зависшего PLC и завершение Stop при активном FC04. **Stop занял 5776 мс** при `RequestTimeoutMs=10000` и возрасте активного запроса `4237 мс` (`RequestInProgress=True`). Это согласуется с ожиданием оставшегося таймаута: мгновенная отмена I/O **не доказана**. Оптимизацию остановки отложить, не блокировать Client. Полностью конкурентный lifecycle и долговременная промышленная надёжность не подтверждены.

## 10. Декодирование polling-данных

Transport публикует исходный `ushort[]`; Core декодирует его согласно карте.

- `Word` преобразуется в `float` без изменения числового значения.
- Для `Float32` использовать **`NModbus.Utility.ModbusUtility.GetSingle(highWord, lowWord)`**, а не отдельную самописную реализацию IEEE-754.
- Подтверждённый прежним NModbus AOT smoke test порядок аргументов: `register[0] = lowWord`, `register[1] = highWord`, затем `GetSingle(highWord, lowWord)`.
- Карта содержит `RegisterOrder`; текущая реализация Core использует перестановки WORD/байтов перед `GetSingle`. Их runtime-проверка на тестовых векторах для всех четырёх вариантов пока не подтверждена.
- Публиковать snapshot только после успешного преобразования всех значений. Не выдавать частично обновлённый массив.

Не переоткрывать вопрос порядка WORD без воспроизводимого теста или противоречия фактическим данным. Принятый путь NModbus является исходным контрактом.

## 11. CoreLink.Transport — существующая реализация сохраняется

Текущие основные компоненты:

- `ModbusTransportSession`;
- `ModbusConnectionManager`;
- `ModbusRequestDispatcher`;
- `ModbusPoller`;
- `ModbusConnectionConfig`.

Transport владеет TCP, NModbus master, таймаутами, reconnect и очередями физических операций. На сессию — одно TCP-соединение и один логический executor запросов.

**Приоритет выполнения:** `Write → Polling Read → Single Read` с реализованной защитой polling от голодания. Уже выполняемый запрос не прерывается ради изменения приоритета.

Core принимает пользовательские команды и транслирует их Transport; не вводить вторую очередь и второй арбитраж. Отдельных соединений для Write и Single Read нет.

Не переписывать проверенный Transport ради нового слоя абстракций. Второй протокол OPC UA сейчас не реализуется.

## 12. Состояния и ошибки

- Отсутствие PLC — штатное эксплуатационное состояние.
- `Running` означает запущенный Core, **не гарантирует наличие данных или соединения**.
- `Disconnected` сообщает об отказе транспорта.
- `NoData` означает отсутствие хотя бы одного успешно опубликованного snapshot.
- `Stopped` означает завершённую работу Core.
- Не проверять связь сравнением значений регистров.
- Ожидаемые сетевые ошибки обрабатывать статусами; не маскировать ошибки программирования состоянием PLC offline.
- `StatusChanged` сообщает о переходах состояния, а не об успешности каждого polling tick.

При ошибках сохранять возможность диагностики. Не добавлять бесконечный повторяющийся информационный лог на каждом неудачном тике без политики ограничения частоты.

## 13. Интеграционные испытания — актуальные факты

**Цепочка в репозитории:** `MapProvider → CoreLinkClient.Start/Stop → ICore → CSharpCoreAdapter → CoreLinkCore → ModbusTransportSession`. В `CoreLink.Client.TestHost` получение snapshot пока вызывается **напрямую через адаптер**, поэтому считать Client интегрированным со snapshot нельзя.

Внешние тестовые приложения (не входят в `CoreLink.Foundation.slnx`): `CoreLink.PlcSimulator` и `CoreLink.CoreSimulator` в проекте `TestCorlink`. PLC Simulator предоставляет TCP Modbus FC04 на `127.0.0.1:1502`, контролируемые `Word/Float32`, режимы stable/cycle/HANG. CoreSimulator работает с реальным `ICore`, показывает значения и статусы.

**Проверено пользователем:** `SnapshotStatus.Ok` с обновлением значений и сопоставлением регистров, отсутствие ложного Ok без данных, отключение и восстановление связи, `NoData` до первого ответа, реакция на HANG с открытым TCP и отсутствием FC04-ответа.

**Последний тест 09.11.2026:** `11:39:44.918 Running`, `11:39:55.029 Disconnected`, `11:41:23.937 STOP BEGIN` с `RequestInProgress=True` и `CurrentRequestAgeMs=4237`, `11:41:29.709 Stopped`. В этой сессии успешных ответов не было, поэтому `SnapshotStatus.NoData` ожидаем.

Выполнен успешный `dotnet build -c Release -t:Rebuild` внешнего CoreSimulator и зависимостей; методом reflection подтверждён `PrintStopDiagnostics` в `CoreLink.Transport.dll`.

**Технический долг:** в `CoreLink.Transport/Modbus/ModbusTransportSession.cs` временные сообщения Stop с `TODO DEBUG`/`FIXME`. Удалить по завершении необходимости в отладке. Не считать диагностические поля стабильным API. Не повторять длительные ручные тесты без отдельного проверяемого вопроса.

**Не доказано:** полный охват отказов, все 4 порядка Float32 на независимых векторах, NativeAOT publish всего приложения, эксплуатационная сертификация.

## 14. NativeAOT

NativeAOT — обязательное требование. NModbus 3.0.83 ранее проверен отдельно на используемых API (включая `ModbusUtility.GetSingle`).

Предыдущий успешный AOT smoke test **не означает**, что новая связка Core + Adapter + Client уже прошла AOT publish. После стабилизации runtime провести проверку конечного исполняемого приложения.

Не использовать без отдельного согласования: runtime reflection, `dynamic`, `Assembly.Load`, `Reflection.Emit`, автоматическое сканирование реализаций и тяжёлые reflection-based DI-схемы.

## 15. Правила инженерной работы с ИИ

**Это обязательные правила, а не рекомендации.**

1. Перед изменением читать текущий `PROMT.md` и реальные исходники затрагиваемых компонентов. Учитывать, что локальный код может опережать GitHub.
2. **Не задавать повторно вопросы, на которые уже отвечает утверждённый контракт.** Не возвращаться к polling interval, GetSnapshot, ownership и порядку WORD без обнаруженного подтверждённого противоречия.
3. Явно отделять `Confirmed` (контракт/сборка/лог), `Inferred` (следствие) и `Unknown` (данных нет). Не выдавать предположения за факт.
4. **Код только в чате, полный файл целиком, один файл за шаг.** Не предлагать фрагментарные правки «замени три строки».
5. Имена и расположение новых файлов согласовывать. Сохранять текущие имена и структуру, если изменение не требуется.
6. Не менять архитектуру, публичные контракты, ABI, ownership, concurrency и зависимости самостоятельно.
7. Не переписывать работающие компоненты без конкретного дефекта или прямого указания.
8. Минимальный diff; не смешивать функциональность с рефакторингом и косметическими переименованиями.
9. Для ожидаемых эксплуатационных отказов использовать детерминированные статусы. Не проглатывать неожиданные ошибки и cancellation.
10. Новые временные участки помечать `FIXME` с причиной и условием удаления. Не оставлять заглушки под видом готовой реализации.
11. Не сообщать «собрано», «проверено» или «пушнуто» без фактического вывода команд или подтверждённого действия.
12. На предоставленный результат сборки или теста сначала отвечать анализом **именно этого результата**; не перескакивать к новым подсистемам.
13. Проверять путь данных, lifecycle, конкурентность, обработку ошибок и cleanup; наличие успешной компиляции не равно доказанной эксплуатационной готовности.
14. При генерации кода делать самопроверку на соответствие существующим API и языку C#/.NET 10. Не включать `preview` как обход проблемы без необходимости.
15. Разработчик утверждает архитектуру и каждую реализацию после личного review. ИИ не принимает технические решения за него.

Порядок: **изучить текущий код → зафиксировать границу задачи → полный файл → build → тест → human review → commit**.

## 17. Следующий этап — CoreLink.Client, подключение ядра
