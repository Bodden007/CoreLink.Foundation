# CoreLink.Foundation — архитектурный промт Core / Client / Rx

**Статус:** согласованная архитектурная концепция, реализация после утверждения  
**Стек:** C# / .NET 10 / NativeAOT / NModbus 3.0.83  
**Репозиторий:** https://github.com/Bodden007/CoreLink.Foundation

## 1. Основной принцип

CoreLink использует два независимых контура:

- **Core Polling** — непрерывный обмен с ПЛК.
- **Client / Rx** — периодическое получение, обработка и публикация значений.

Core Polling работает независимо от Client / Rx. Медленная обработка Rx не останавливает polling и не управляет TCP-соединением.

**CoreLink.Client — единственная публичная точка управления системой.**

## 2. Ответственность компонентов

### CoreLink.Client

- Загружает карту регистров.
- Создаёт один `float[]` на жизненный цикл сессии.
- Является единственным владельцем клиентского массива.
- Инициализирует и запускает Core и Rx.
- Управляет Start / Stop и контролирует состояние системы.
- Запускает цикл получения snapshot с периодом 500 мс.
- Временно закрепляет массив через `fixed`.
- Передаёт Core указатель и длину массива.
- Синхронно ожидает результат заполнения.
- После выхода из `fixed` передаёт массив Rx при успешном результате.
- Ожидает завершения обработки Rx (`Ready`).
- Предоставляет внешнему приложению одиночные Read / Write.

### CoreLink.Core

- Управляет собственным polling.
- Использует существующий Modbus Transport.
- Хранит последние успешно полученные и декодированные значения.
- Обеспечивает согласованность внутреннего snapshot.
- По запросу Client синхронно копирует значения в переданную память.
- Не сохраняет указатель и не владеет клиентским массивом.
- Возвращает результат операции заполнения.
- Выполняет одиночные Read / Write через существующий Dispatcher.
- Не зависит от Rx, Avalonia и UI.

### CoreLink.Rx

- Получает клиентский массив после завершения `GetSnapshot`.
- Синхронно читает и обрабатывает значения.
- Уведомляет подписчиков о новых значениях.
- Не изменяет исходный массив.
- Не сохраняет исходный массив для отложенного использования.
- Не передаёт подписчикам ссылку на исходный массив.
- После завершения обработки и синхронных уведомлений возвращает `Ready`.
- Не обращается непосредственно к Core или Transport.

## 3. Цикл Client / Rx

Период запуска — **500 мс между началами итераций**.

```text
                 PLC
                  │
                  ▼
             Core Polling
                  │
                  ▼
              Core Data
                  │
                  │
Client ── GetSnapshot(ptr, length) ──► Core
   ▲                                      │
   │                                      │
   ◄──────── Result / Status ─────────────┘
   │
   ▼
Выход из fixed
   │
   ├── Ошибка → обработка статуса
   │
   └── Ok
        │
        ▼
     Rx.Process(buffer)
        │
        ├── Обработка
        ├── Уведомление подписчиков
        │
        ▼
       Ready
        │
        ▼
  Следующий период 500 мс
```

Правила:

1. Client запускает получение snapshot по расписанию.
2. Одновременно выполняется не более одной итерации Client / Rx.
3. Если обработка длится более 500 мс, следующая итерация ожидает завершения предыдущей.
4. Пропущенные итерации не накапливаются.
5. Повторное заполнение разрешается только после `Ready`.
6. Core Polling продолжает работу независимо.

**GetSnapshot не выполняет Modbus-запрос.**

## 4. Контракт памяти

### Создание и владение

- Client создаёт `float[]` один раз при инициализации сессии.
- Размер определяется картой регистров.
- Один массив переиспользуется во всех циклах.
- При повторном Start после полного Stop создаётся новый массив для новой сессии.
- Core и Rx не становятся владельцами массива.

### Pinning и указатели

- Client использует `fixed` исключительно на время синхронного вызова `Core.GetSnapshot`.
- Core получает `float*` и длину массива.
- Core имеет временное право записи.
- Core не сохраняет указатель.
- Core не освобождает переданную память.
- Core полностью прекращает доступ к указателю до возврата управления.
- После возврата из `GetSnapshot` Client выходит из `fixed`.
- Указатель не используется за пределами операции заполнения.

### Чтение Rx

- После выхода из `fixed` Rx использует исключительно безопасные управляемые типы.
- Предпочтительный контракт чтения — `ReadOnlySpan<float>`.
- Сырые указатели `float*` в Rx запрещены.
- Rx не изменяет исходные значения.
- Rx не сохраняет ссылки на исходный массив для последующей обработки.
- Подписчики не получают исходный массив или указатели.
- Подписчикам передаются отдельные значения.
- `Ready` подтверждает завершение всех операций чтения исходного массива.

**Memory safety:** указатель не переживает `fixed`.

**Data consistency:** доступ Rx к исходному массиву не переживает `Ready`.

Дополнительных массивов и копирования Client → Rx нет.

## 5. Согласованность данных Core

Core хранит последние полученные от ПЛК значения.

При успешном polling:

1. Transport получает регистры.
2. Core декодирует значения согласно карте.
3. Core согласованно обновляет внутреннее состояние.
4. Завершённый snapshot становится доступным Client.

Операция `GetSnapshot` должна возвращать согласованный набор значений, без смешивания разных циклов обновления.

Синхронизация внутреннего состояния Core не должна удерживать блокировку на время сетевого Modbus-запроса.

Конкретный механизм синхронизации утверждается при реализации.

## 6. Одиночные Read / Write

Client предоставляет:

- `Read` — одиночное чтение регистров.
- `WriteSingle` — запись одного регистра.
- `WriteMultiple` — запись блока регистров.

Маршрут:

```text
Application
    │
    ▼
CoreLink.Client
    │
    ▼
CoreLink.Core
    │
    ▼
ModbusTransportSession
    │
    ▼
ModbusRequestDispatcher
    │
    ▼
PLC
```

Требования:

- Используется существующее TCP-соединение.
- Все операции проходят через существующий Dispatcher.
- Сохраняются приоритеты Write → Polling Read → Single Read.
- Read / Write не зависят от Client / Rx snapshot-цикла.
- Операции не останавливают штатный polling.
- Client не обращается непосредственно к Transport.
- Результаты возвращаются с явными статусами.

## 7. Результаты и ошибки

Операция snapshot должна различать:

- `Ok` — согласованный snapshot успешно скопирован.
- `NoData` — значения ещё не получены.
- `Disconnected` — соединение отсутствует.
- `BadBuffer` — некорректный указатель или длина.
- `Stopped` — Core остановлен.

Точные имена и сигнатуры результатов утверждаются отдельно.

Ошибки связи не кодируются технологическими значениями `NaN`, `-9999` и другими специальными числами.

Последние полученные данные не должны автоматически считаться актуальными после потери связи.

Ошибки Rx не должны останавливать Core Polling. Политика обработки ошибок подписчиков требует отдельного согласования.

## 8. Lifecycle

Client управляет жизненным циклом всей системы.

При Start:

1. Загружает карту.
2. Создаёт клиентский буфер.
3. Инициализирует Core.
4. Инициализирует Rx.
5. Запускает Core.
6. Запускает цикл Client / Rx.

При Stop:

1. Прекращает запуск новых итераций Client / Rx.
2. Дожидается завершения активной обработки.
3. Останавливает Core и его polling.
4. Дожидается завершения активных операций Transport.
5. Освобождает ресурсы и ссылку на клиентский буфер.

Нельзя освобождать используемую память до полного завершения операций.

## 9. Изменения ICore

Текущий контракт:

```csharp
CoreStatus Start(CoreMap coreMap, float[] coreBuffer);
CoreStatus Stop();

event Action? BufferReady;
event Action<CoreStatus>? StatusChanged;
```

Требуемые изменения:

- Удалить передачу массива при Start.
- Удалить `BufferReady` для snapshot.
- Добавить синхронную операцию `GetSnapshot` с указателем, длиной и результатом.
- Сохранить уведомления о состоянии Core.
- Предусмотреть Read / Write.
- Обеспечить корректное завершение активных операций при Stop.

Точные сигнатуры, результаты и модель асинхронной остановки согласовать до написания кода.

## 10. Архитектурные ограничения

Без согласования не добавлять:

- Дополнительные буферы Client / Rx.
- Копирование массива между Client и Rx.
- Очередь snapshot.
- Отдельный асинхронный цикл Rx.
- Callback `BufferReady` для получения snapshot.
- Прямой доступ Rx к Core или Transport.
- Постоянный pinning клиентского массива.
- Передачу сырых указателей подписчикам.
- Новое TCP-соединение для одиночных операций.
- Изменения существующего Modbus polling и Dispatcher.
- Лишние интерфейсы, фабрики и архитектурные слои.
- Runtime reflection и несовместимые с NativeAOT механизмы.

## 12. Главный инвариант

**Core** независимо опрашивает ПЛК, хранит согласованные данные и синхронно копирует snapshot по запросу.

**Client** управляет системой, владеет единственным `float[]`, временно закрепляет его через `fixed`, получает snapshot, передаёт массив Rx и ожидает `Ready`.

**Rx** синхронно читает значения через безопасные managed-типы, уведомляет подписчиков и подтверждает завершение обработки.

**Указатели существуют только во время GetSnapshot. Обработка Rx не влияет на Core Polling.**
