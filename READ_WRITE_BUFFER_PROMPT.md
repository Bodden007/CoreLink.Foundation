# CoreLink — контракт временных буферов для разовых Read/Write

> Архитектурный промт / спецификация для последующей реализации. Статус: концепция, код не изменён. Дата: 12.11.2026.
>
> Приоритет: correctness → ownership/lifetime → отказоустойчивость → предсказуемость аллокаций → оптимизация. Любая реализация требует ручного архитектурного и кодового review.

## 1. Назначение и границы

Данный документ фиксирует управление памятью при разовых одиночных и групповых операциях чтения/записи PLC через CoreLink.Foundation.

- **Polling** работает по собственной карте, со своим snapshot и Rx; разовые Read/Write не используют и не меняют карту polling или snapshot.
- **Client** — публичная точка вызова, владелец временных клиентских буферов и закрепления памяти.
- **Core** проверяет входные данные, преобразует логические адреса в используемые протоколом адреса, интерпретирует Word/Float32 и выполняет разовый запрос.
- **Dispatcher / Transport** выполняют запросы через существующую TCP-сессию, без отдельного соединения, отдельного worker или второго polling.
- **Потребитель** (например, ViewModel окна Avalonia) владеет долговременным буфером результата. CoreLink не знает об окнах и не управляет их жизненным циклом.

Не заменять текущий ReadAsync по ValueId молча: это уже существующий публичный API, а новый адресный Single/Batch контракт требует отдельного согласования совместимости.

## 2. Два пути вызова

### Single

- Прямой вызов с **логическим адресом** и явно заданным типом `Word` либо `Float32`; при Write — также типизированным значением.
- Отдельное бинарное описание и отдельный клиентский временный буфер **не создаются**.
- Single Read возвращает значение и статус; Single Write возвращает статус.
- `Word` занимает один регистр, `Float32` два последовательных регистра, начиная с указанного адреса.
- Конкретные публичные сигнатуры и выбор функции одиночного Read ещё подлежат согласованию; не придумывать API в реализации.

### Batch

- Один **временный бинарный дескриптор разового запроса**: логический стартовый адрес и последовательность типов значений (`Word`/`Float32`); для Write дополнительно передаются сами типизированные значения. Порядок элементов задаёт порядок регистров.
- Этот дескриптор **не является CoreMap**, не содержит карту polling и не меняет конфигурацию сессии.
- Для Batch Read Client арендует временный выходной буфер и при необходимости закрепляет его на время доступа Core; для Batch Write — временные входные данные/буфер по утверждённому контракту. Операции разовые.
- Для группового Write — только один непрерывный диапазон и один FC16, до 123 физических регистров; отсутствие разрывов, перекрытий и превышения границ проверяется **до отправки**. Никакого автоматического разбиения на несколько запросов.
- Для группового Read формат результата должен сохранять интерпретацию смешанных значений; соответствие элементов их типам задаётся дескриптором. Способ представления результата в публичном API требуется согласовать.

## 3. Адреса, типы и протокол

- Пользователь задаёт **логический** начальный адрес, Core преобразует его в адрес, используемый Modbus.
- Для `Word` — один регистр, для `Float32` — два, начиная с переданного адреса. Пользователь не рассчитывает адрес второго слова.
- `RegisterOrder` — **общий для одной сессии**, одинаковый для polling, Read и Write; не дублируется в каждом запросе.
- FC06 — одиночная запись Word; FC16 — запись Float32 либо группы; подтверждение Modbus считается успешным выполнением Write на уровне протокола, **не** подтверждением применения уставки прикладной логикой PLC.
- Write не выполняет контрольного чтения, не изменяет snapshot и не повторяется автоматически после ошибки.
- При Timeout судьба записи **неизвестна**: PLC мог применить её до потери ответа. Поздний автоматический retry запрещён.

## 4. Ownership: какие буферы существуют

| Ресурс | Владелец | Lifetime |
| --- | --- | --- |
| Временный дескриптор Batch | Client | Один вызов; не хранится после завершения |
| Временный рабочий буфер Batch | Client | Rent → использование Core → Unpin → Return, включая ошибки |
| Указатель / pinning | Client | Только разрешённое время доступа Core; освобождается в finally |
| Внутренние данные NModbus/Dispatcher | Core/Transport | По существующему lifecycle; не зависят от клиентского указателя |
| Буфер результата окна | Вызывающая сторона / ViewModel | До закрытия/освобождения владельцем; может переиспользоваться |

- Рекомендуемый механизм повторного использования временного **managed** буфера — `ArrayPool<T>`. `Rent(length)` может вернуть более длинный массив: различать фактическую ёмкость и логическую длину запроса.
- `Return()` не гарантирует немедленного уничтожения массива: он возвращается пулу. `Unpin`/`GCHandle.Free()`/`MemoryHandle.Dispose()` снимает закрепление немедленно, но не удаляет managed-массив из памяти GC.
- Не возвращать массив в пул, пока любой код Core/Transport может обратиться к его памяти.
- `ArrayPool` не является обязательным для Single и не должен появляться там без необходимости.
- Не создавать новый массив результата на каждом успешном Read, если вызывающая сторона уже имеет подходящий постоянный буфер.

## 5. Путь Batch Read и момент освобождения памяти

1. Потребитель заранее создаёт **собственный буфер результата** нужного размера (например, в ViewModel) и владеет им в течение времени жизни окна.
2. Client принимает разовый Read, валидирует структуру запроса, формирует временный бинарный дескриптор и арендует временный рабочий буфер необходимой логической длины.
3. Client закрепляет временную память, если интерфейс с Core требует указатель, и вызывает Core. **Запрещено** использовать обычный `fixed` через `await`; pinning должен иметь корректный lifetime при асинхронности.
4. Core декодирует описание, исполняет разовый Read через существующий Dispatcher/Transport. Зависший внутренний сетевой I/O не получает и не сохраняет указатель на клиентскую память.
5. При `Ok` Core записывает согласованный результат в доступный Client буфер. При любой ошибке результат считается непригодным для публикации.
6. Client получает окончательный статус. При `Ok` и если потребитель ещё активен — копирует **только логически действительную часть** из временного буфера в буфер потребителя. При ошибке или отмене не копирует.
7. В `finally` Client **в любом случае** снимает pinning и возвращает арендованный буфер в пул. Возвращать буфер даже при ошибке, отмене, Stop/Timeout.
8. Client возвращает вызывающей стороне статус; при успехе буфер потребителя уже содержит новые данные. Время жизни этого буфера принадлежит потребителю, а не CoreLink.

Переиспользование буфера ViewModel возможно только если отсутствует конкурентная запись/чтение того же массива без синхронизации. CoreLink не публикует половину результата как успешный Read. Если для запроса необходимо проверить весь ответ перед публикацией, сначала проверять данные во временном буфере.

## 6. Путь Batch Write

1. Потребитель задаёт логический начальный адрес, последовательность типов и значения.
2. Client формирует временный запрос/буфер; Core валидирует всю группу, кодирует Word/Float32 в последовательность регистров с общим `RegisterOrder`.
3. Dispatcher получает собственное независимое содержимое запроса до момента возврата/повторного использования клиентского буфера. В текущем Dispatcher массив для FC16 **клонируется при постановке в очередь**; не удалять эту гарантию без нового ownership-контракта.
4. Выполняется один FC16 (для Single Word — FC06). Внешний результат Write — статус, **без** буфера чтения и без контрольного Read.
5. По завершении, включая Timeout/Stop/Failed, Client освобождает pinning и возвращает свои временные ресурсы в `finally`. После возврата клиентского буфера любые поздние действия NModbus не должны читать его память.
6. Никаких повторов команды по инициативе CoreLink после ошибок; при Timeout факт применения команды неизвестен.

## 7. Отмена, закрытие окна, Stop, Timeout

- Закрытие окна инициирует `CancellationToken` для принадлежащих ему разовых вызовов и запрещает публикацию позднего результата в закрытое окно.
- `try/catch` нужен для превращения ошибок в предусмотренные статусы; **`finally` обязателен** для Unpin/Return независимо от исхода.
- Отмена не доказывает, что внутренний NModbus I/O физически остановился. Контракт гарантирует другое: после выдачи результата Core/Transport не обращаются к клиентскому указателю. Фоновая незавершённая операция использует только собственную память и подчиняется существующей логике отбраковки/закрытия сессии.
- На стороне Client можно дождаться логического завершения операции, прекратить публикацию и вернуть временную память. ViewModel не уничтожает буфер, пока существует активная операция копирования в него; managed-массив не «удаляется» немедленно при закрытии окна.
- `Ok` публикует полный результат; `Timeout`, `Disconnected`, `Stopped`, `Failed`, ошибка дескриптора — статус без частичной публикации.
- При конкурентных операциях Read и Close/Stop должен быть единственный определённый путь завершения и освобождения ресурса.

## 8. Инварианты для code review

1. CoreMap и карта polling **никак не участвуют** в адресации разовых Read/Write.
2. Single не требует временного бинарного дескриптора/клиентского буфера.
3. Batch допускает смешанные Word/Float32; количество **значений** и количество **Modbus-регистров** считаются отдельно.
4. На каждый успешный Rent приходится ровно один Return; на каждый pin — ровно один Unpin, в том числе при исключении.
5. **Никто не обращается к указателю после возврата статуса**; не существует скрытого «отложенного писателя» в освобождённый буфер.
6. Во время копирования в буфер потребителя он остаётся доступным; при Cancel/Close поздний результат не публикуется.
7. При ошибке нет частично опубликованного Read; Write не дублируется автоматически.
8. Dispatcher сохраняет существующие приоритеты и одну TCP-сессию; новый разовый вызов не создаёт свой Transport.
9. Никаких `object`, `dynamic`, reflection, неявной конвертации пользовательских типов или новых архитектурных слоёв.
10. Новые интерфейсы/формат бинарного описания и изменение существующего `ReadAsync` согласовываются отдельно. Документ не является разрешением менять production-код.

## 9. Проверки реализации

- Последовательные Batch Read разной длины (например, 10 → 5 → 10), включая возврат буфера в пул.
- Параллельные вызовы с разными размерами: отсутствие перезаписи общих данных.
- Смешанные Word/Float32; точный счёт регистров и проверка RegisterOrder.
- Закрытие окна во время Read и одновременный Stop.
- Timeout/Hang/Offline/Recovery: безопасный Unpin/Return и отсутствие позднего доступа к клиентской памяти.
- Проверка, что ошибочный Read не изменяет постоянный буфер ViewModel.
- FC16: непрерывность, лимит 123 регистра, единственный запрос, отсутствие retry.
- Замеры allocations/GC и длительности pinning; оптимизацию делать только после измерений.

## 10. Правило дальнейшей разработки

Это **контракт управления памятью**, не готовый API и не реализация. Сначала сверить с действующими ICore/CoreLinkClient, отдельно согласовать формат бинарного Batch и способ типизированного результата, затем изменять по одному логическому шагу: build → test → review → commit. Не переписывать polling и существующий Dispatcher ради нового Read/Write.
