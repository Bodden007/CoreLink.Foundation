# CoreLink — управление буферами разовых Read/Write

> Архитектурный промт / спецификация для последующей реализации. Статус: концепция, код не изменён. Дата: 12.11.2026.
>
> Приоритет: correctness → ownership/lifetime → отказоустойчивость → предсказуемость аллокаций → оптимизация. Любая реализация требует ручного архитектурного и кодового review.

## 1. Назначение и границы

Данный документ фиксирует управление памятью при разовых одиночных и групповых операциях чтения/записи PLC через CoreLink.Foundation.

- **Polling** работает по собственной карте, со своим snapshot и Rx; разовые Read/Write не используют и не меняют карту polling или snapshot.
- **Client** — публичная точка вызова, владелец закрепления памяти (pinning) на время операции; не владеет массивом результата ViewModel.
- **Core** проверяет входные данные, преобразует логические адреса в используемые протоколом адреса, интерпретирует Word/Float32 и выполняет разовый запрос.
- **Dispatcher / Transport** выполняют запросы через существующую TCP-сессию, без отдельного соединения, отдельного worker или второго polling.
- **Потребитель** (например, ViewModel окна Avalonia) владеет долговременным буфером результата. CoreLink не знает об окнах и не управляет их жизненным циклом.

Не заменять текущий ReadAsync по ValueId молча: это уже существующий публичный API, а новый адресный Single/Batch контракт требует отдельного согласования совместимости.

## 2. Два пути вызова

### Single

- Прямой вызов с **логическим адресом** и явно заданным типом `Word` либо `Float32`; при Write — также типизированным значением.
- Отдельное бинарное описание и отдельный клиентский временный буфер **не создаются**.
- Single Read возвращает значение и статус; Single Write возвращает статус.
- `Word` занимает один регистр, `Float32` два последовательных регистра, начиная с указанного адреса.
- Конкретные публичные сигнатуры и выбор функции одиночного Read ещё подлежат согласованию; не придумывать API в реализации.

### Batch

- Один **временный бинарный дескриптор разового запроса**: логический стартовый адрес и последовательность типов значений (`Word`/`Float32`); для Write дополнительно передаются сами типизированные значения. Порядок элементов задаёт порядок регистров.
- Этот дескриптор **не является CoreMap**, не содержит карту polling и не меняет конфигурацию сессии.
- Для Batch Read потребитель заранее выделяет массив результата и передаёт его Client; Client закрепляет именно этот массив и передаёт указатель Core. Нет временного выходного буфера Client, ArrayPool и промежуточного копирования. Для Batch Write Client передаёт значения по отдельному входному контракту; выходной буфер значений не требуется.
- Для группового Write — только один непрерывный диапазон и один FC16, до 123 физических регистров; отсутствие разрывов, перекрытий и превышения границ проверяется **до отправки**. Никакого автоматического разбиения на несколько запросов.
- Для группового Read формат результата должен сохранять интерпретацию смешанных значений; соответствие элементов их типам задаётся дескриптором. Способ представления результата в публичном API требуется согласовать.

## 3. Адреса, типы и протокол

- Пользователь задаёт **логический** начальный адрес, Core преобразует его в адрес, используемый Modbus.
- Для `Word` — один регистр, для `Float32` — два, начиная с переданного адреса. Пользователь не рассчитывает адрес второго слова.
- `RegisterOrder` — **общий для одной сессии**, одинаковый для polling, Read и Write; не дублируется в каждом запросе.
- FC06 — одиночная запись Word; FC16 — запись Float32 либо группы; подтверждение Modbus считается успешным выполнением Write на уровне протокола, **не** подтверждением применения уставки прикладной логикой PLC.
- Write не выполняет контрольного чтения, не изменяет snapshot и не повторяется автоматически после ошибки.
- При Timeout судьба записи **неизвестна**: PLC мог применить её до потери ответа. Поздний автоматический retry запрещён.

## 4. Ownership: какие буферы существуют

| Ресурс | Владелец | Lifetime |
| --- | --- | --- |
| Временный бинарный дескриптор Batch | Client | Один вызов; освобождается после использования Core |
| Массив результата Batch Read | Потребитель (например, ViewModel) | Создаётся один раз и переиспользуется, пока живёт владелец |
| Закрепление массива / указатель | Client | С начала операции до получения статуса; освобождение в `finally` |
| Внутренние данные NModbus/Dispatcher | Core/Transport | По lifecycle внутренней операции; не удерживают клиентский указатель |
| Входные значения Batch Write | Потребитель; Core/Dispatcher получают необходимые данные для выполнения | Не должны изменяться вызывающим кодом до принятия их независимой копии либо окончания запроса |

- **Нет ArrayPool, дополнительного временного выходного массива и копирования результата Client → ViewModel** в основном пути Batch Read.
- ViewModel/потребитель создаёт массив заранее, передаёт его Client и сохраняет владение. CoreLink не знает о времени жизни окна.
- Client закрепляет managed-массив на **всё время логической операции**, включая ожидание Modbus. Использовать механизм с явным временем жизни (например, `GCHandle`), поскольку обычный `fixed` не должен пересекать `await`.
- При любом результате Client обязательно снимает закрепление в `finally`. Unpin не уничтожает managed-массив: он остаётся у ViewModel и затем управляется GC после утраты ссылок.
- Core не сохраняет указатель после завершения операции. Любой зависший внутренний NModbus I/O использует **собственную** память, а не память ViewModel.
- Один буфер используется **одной активной операцией за цикл**. Отсутствие конкурентной записи в тот же массив — явное условие контракта; сериализация Modbus-запросов через Dispatcher сама по себе не защищает UI от чтения массива во время записи.
- ViewModel использует новые данные только после успешного статуса `Ok`. Содержимое массива нельзя читать как новый согласованный результат до завершения операции.

## 5. Путь Batch Read и момент освобождения памяти

1. Потребитель (например, ViewModel) **один раз создаёт массив** необходимой длины и передаёт его Client вместе с запросом Read.
2. Client проверяет достаточность длины, формирует временный бинарный дескриптор для Batch и закрепляет **тот же массив ViewModel**. Дополнительного массива Client не создаёт.
3. Client передаёт Core дескриптор, указатель и логическую длину. Закрепление остаётся действительным до возврата статуса Core.
4. Core декодирует запрос, проверяет весь диапазон и выполняет разовый Read через существующий Dispatcher/Transport. Сетевой I/O не записывает непосредственно в память ViewModel.
5. Core **сначала получает, декодирует и проверяет полный результат во внутренних данных**. Только если вся операция успешна, синхронно заполняет массив ViewModel по указателю.
6. Если результат `Timeout`, `Disconnected`, `Stopped`, `Failed` или другая ошибка, **заполнение не начинается; массив ViewModel остаётся неизменным**. Это обязательный инвариант, не просто игнорирование данных после ошибки.
7. Core возвращает единый статус, гарантируя, что никакая его задача больше не обращается к указателю. Client снимает закрепление **при любом исходе** в `finally`.
8. При `Ok` потребитель получает уведомление об успехе и использует свой уже заполненный массив. При ошибке получает статус; тот же массив может быть использован при следующем вызове. После закрытия окна владелец прекращает использование массива и снимает свои ссылки.

**Важно:** запись нескольких элементов массива не является атомарной операцией CPU. Принятое правило «одна операция за цикл» исключает конкурирующие операции заполнения; потребитель также не должен читать массив во время заполнения. Для гарантии «при не-Ok массив не изменился» все ошибки проверки/декодирования должны быть выявлены **до первой записи**. Исключительный сбой в середине самой записи потребует отдельного решения; не объявлять эту гарантию автоматически доказанной компилятором.

## 6. Путь Batch Write

1. Потребитель задаёт логический стартовый адрес, последовательность типов и типизированные значения.
2. Client формирует временное описание Batch Write; Core проверяет весь запрос и преобразует Word/Float32 в последовательность регистров по общему `RegisterOrder`.
3. Dispatcher получает собственные независимые данные для FC16. В текущем коде массив FC16 **клонируется при постановке в очередь**. Клиентская память не должна использоваться отложенным запросом после возврата статуса.
4. Выполняется один FC16 (для Single Word — FC06). Результат записи — только статус; выходной массив и контрольное чтение не нужны.
5. Если для передачи входных данных применён pinning, Client снимает его **при любом исходе** в `finally`. Временный бинарный дескриптор освобождается после прекращения использования Core.
6. После `Timeout` судьба команды неизвестна. Автоматический повтор запрещён. Запись не изменяет snapshot.

## 7. Отмена, закрытие окна, Stop, Timeout

- Закрытие окна инициирует отмену принадлежащей ему операции (`CancellationToken`) и запрещает публикацию позднего результата. До завершения доступа Core к массиву владелец не должен его переиспользовать в другой операции.
- `try/catch` преобразует ожидаемые ошибки в предусмотренные статусы; **`finally` безусловно освобождает pinning** при `Ok`, `Timeout`, `Disconnected`, `Stopped`, `Failed`, отмене и исключении.
- Отмена не гарантирует мгновенного физического завершения NModbus. Core обязан завершить **любое использование указателя**, прежде чем возвратить статус. Поздняя внутренняя сетевая задача не имеет указателя на массив ViewModel.
- Память массива ViewModel не «удаляется» в Client: она принадлежит потребителю. После закрытия окна и исчезновения ссылок массив будет собран GC; указатель снимается сразу после операции.
- Отрицательный статус Read не изменяет массив; пользовательская запись в него происходит только после успешной полной проверки и до `Ok`.
- Контракт **одна активная операция на буфер за цикл** принимается как ограничение вызывающей стороны. Если в дальнейшем появятся конкурентные вызовы с одним массивом, понадобится отдельная координация.

## 8. Инварианты для code review

1. CoreMap и polling не участвуют в прямых Read/Write.
2. Single — прямые параметры/результат, без временного бинарного описания или массива Client.
3. Batch — смешанные Word/Float32; количество значений отличается от количества Modbus-регистров.
4. **Batch Read заполняет массив потребителя непосредственно**, без промежуточного выходного массива Client, ArrayPool или копирования Client → ViewModel.
5. Один pin → один Unpin в `finally` при любом исходе. Pinning может длиться на протяжении всего асинхронного вызова.
6. **При статусе, отличном от Ok, массив потребителя не изменяется.** Проверка всего результата предшествует заполнению.
7. После возврата статуса никто в Core/Transport не обращается к клиентскому указателю, включая зависшие/поздние I/O.
8. Один буфер обслуживает одну активную операцию; не выполняются конкурентные заполнения. UI не читает массив во время записи.
9. Write не повторяется автоматически; Dispatcher и одна TCP-сессия используются повторно, без нового транспорта.
10. Никаких `object`, `dynamic`, reflection или скрытого преобразования типов.
11. Изменение существующего `ReadAsync(ValueIds)`, формат Batch и новые публичные сигнатуры согласовать отдельно. Документ не является разрешением менять production-код.

## 9. Проверки реализации

- Batch Read с повторно используемым массивом потребителя: длина 10, затем 5, затем 10; проверка логической длины и отсутствия лишних записей.
- Смешанные Word/Float32, корректное число регистров и `RegisterOrder`.
- Ошибка в середине получения/декодирования: **буфер остаётся побайтно неизменным**, статус не `Ok`.
- Timeout/Hang/Offline/Recovery: после статуса нет позднего обращения к указателю, pinning снят.
- Закрытие окна во время Read, отмена и одновременный Stop.
- Проверка, что не возникло двух одновременных записей в один массив.
- FC16: непрерывность, максимум 123 регистра, один запрос, отсутствие retry.
- Замеры времени pinning и GC/аллокаций — только после корректной реализации.

## 10. Правило дальнейшей разработки

Это **контракт управления памятью**, не готовый API и не реализация. Сначала сверить с действующими ICore/CoreLinkClient, отдельно согласовать формат бинарного Batch и способ типизированного результата, затем изменять по одному логическому шагу: build → test → review → commit. Не переписывать polling и существующий Dispatcher ради нового Read/Write.
