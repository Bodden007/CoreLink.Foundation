# CoreLink.Client — архитектурные контракты

**Проект:** CoreLink.Foundation  
**Дата фиксации концепции:** 10.11.2026  
**Статус:** согласованная концепция; не все публичные API и механизмы реализованы.  
**Источник правил:** [PROMT.md](PROMT.md). Этот документ уточняет контракт Client; фактические исходники имеют приоритет при описании текущей реализации.

## 1. Назначение

`CoreLink.Client` — единая публичная точка взаимодействия внешнего приложения с инфраструктурой CoreLink.Foundation и центральный координатор её жизненного цикла.

Client **координирует**, но не подменяет обязанности Core, Transport и Rx. Внешнее приложение (Avalonia View/ViewModel) взаимодействует с CoreLink через Client, не управляя его внутренними компонентами.

```text
Avalonia / ViewModel
       |
       v
CoreLink.Client  <---->  CoreLink.Rx  ----> подписчики приложения
       |
      ICore
       |
CoreLink.Adapter.CSharp
       |
CoreLink.Core
       |
CoreLink.Transport
       |
      PLC
```

Стрелка Client ↔ Rx означает: Rx запрашивает snapshot **через Client**; Client получает результат через ICore и передаёт его Rx. Прямого обращения Rx к ICore нет. Конкретные сигнатуры интеграции не утверждены.

## 2. Ответственность Client — Confirmed

1. Загружает карту по `mapId` и создаёт клиентский буфер значений `float[]` для сессии.
2. Создаёт, запускает, останавливает и освобождает `CoreLink.Rx`; владеет его lifecycle.
3. Передаёт в Core бинарную карту регистров v2 посредством существующего `ICore.Start(CoreMap)`.
4. По запросу/готовности Rx получает последний snapshot через `ICore.GetSnapshot`; Client **не содержит собственного независимого периодического цикла чтения snapshot**.
5. Принимает `SnapshotStatus` и, при успехе, значения; при неуспехе не выдаёт прежний буфер как свежие данные.
6. Передаёт в Rx данные или результат/статус запроса; конкретный публичный контракт передачи ещё не утверждён.
7. Управляет запуском/остановкой инфраструктуры и получает статусы Core через `ICore.StatusChanged`.
8. Предоставляет внешнему приложению операции чтения и записи одиночных регистров и последовательных блоков **через Core**, а не через Rx. Требование принято концептуально; сигнатуры и расширение `ICore` ещё не утверждены.
9. При завершении закрывает путь новых операций, останавливает Rx, завершает Core и освобождает принадлежащие Client ресурсы.
10. Служит единой точкой взаимодействия View/ViewModel с инфраструктурой.

Client **не** выполняет Modbus polling, TCP reconnect, декодирование регистров, преобразование физических единиц или Rx-обработку данных. Client **не** реализует отдельный механизм автоматического перезапуска Core.

## 3. Границы компонентов

| Компонент | Владеет / выполняет | Не выполняет |
| --- | --- | --- |
| Client | Конфигурация сессии, клиентский буфер, lifecycle Core и Rx, маршрутизация snapshot/status/Read/Write | Протокол, декодирование, фильтрация, reconnect |
| Core | Декодирование бинарной карты, `ushort[] → float[]`, последний согласованный snapshot, Core state, Transport session | UI и Rx-подписки |
| Transport | TCP/Modbus, polling, таймауты, reconnect, сериализация запросов и арбитраж операций | Клиентский буфер и UI |
| Rx | Запрос snapshot через Client, реактивная обработка/публикация, общий поток подписчикам | Прямой доступ к ICore/Transport и физические команды PLC |
| View / ViewModel | Подписка через публичный API Client, представление данных и статусов | Создание и управление Core/Transport/Rx |

**Два разных вида преобразований:** техническое декодирование Word/Float32 и порядка регистров **уже принадлежит Core**. Прикладные преобразования после получения `float[]` относятся к инфраструктуре Rx (при необходимости совместно с Units); конкретный состав не определён. Client не преобразует значения.

## 4. Два независимых цикла

**Транспортный цикл:** `PLC → Transport polling → ushort[] → Core decode → Core snapshot`. Polling задаётся картой и не зависит от UI или Rx.

**Потребительский цикл:** `Rx (готовность/запрос) → Client → ICore.GetSnapshot → Client buffer/status → Rx → подписчики`.

- `GetSnapshot` синхронно копирует готовое состояние и **не выполняет Modbus-запрос**.
- Client не накапливает историю и не запускает собственный таймер для snapshot.
- Ориентир 500 мс из ранее обсуждавшихся тестов не становится обязательным интервалом Client; период или стратегия запроса Rx должны быть согласованы отдельно.
- Несколько подписчиков используют один Rx-поток; при открытии экрана он подписывается, при закрытии — вызывает `Dispose()` своей подписки.
- Основные подписчики создаются/подключаются при старте приложения. Новые подписчики ожидают следующую публикацию общего hot stream: обязательного replay последнего значения нет.
- Закрытие одного экрана не останавливает Rx, Core или Transport и не влияет на другие подписки.

## 5. Буфер и согласованность данных

- Client выделяет один `float[]` на сессию размером `CoreMap.BufferLength` (это число значений, а не размер бинарной карты в байтах).
- Client временно закрепляет буфер через `fixed` при синхронном `ICore.GetSnapshot(float*, int)`; Core никогда не хранит указатель.
- Core владеет собственным последним согласованным snapshot; данные заменяются только после успешного декодирования.
- При `SnapshotStatus != Ok` клиентский буфер не модифицируется Core и **не публикуется как свежий**.
- Не допускать гонки между чтением snapshot, публикацией в Rx и остановкой/освобождением буфера. Способ синхронизации Client/Rx ещё не согласован.
- Время жизни данных, доступных асинхронным подписчикам, и политика копирования/неизменяемости при публикации в Rx ещё не утверждены; нельзя молча передать переиспользуемый mutable массив как стабильный snapshot.

## 6. Статусы: три разных контракта

### 6.1. `CoreStatus` — существующий статус ядра

`Running`, `Stopped`, `Disconnected`, `Reconnecting`, `BadConfig`, `Error`.

Core сообщает изменения через `ICore.StatusChanged`. `Running` означает запущенную работу Core и **не является безусловным доказательством наличия свежего snapshot**. `Reconnecting` существует в enum; фактические переходы в него требуют проверки перед привязкой к View.

### 6.2. `SnapshotStatus` — существующий результат `GetSnapshot`

`Ok`, `NoData`, `Disconnected`, `BadBuffer`, `Stopped`.

- `Ok`: значения успешно скопированы.
- `NoData`: ещё нет успешного snapshot.
- `Disconnected`: ранее полученные значения устарели; они не копируются в Client как свежие.
- `BadBuffer`: ошибка предоставленного буфера.
- `Stopped`: ядро остановлено.

`NoData` сам по себе не доказывает физического отключения PLC.

### 6.3. `CoreLinkState` — существующий внутренний lifecycle Client

`Created`, `Starting`, `Running`, `Suspended`, `Stopping`, `Stopped`, `Faulted`.

Этот статус управляет допустимостью операций Client. Не подменять им состояние PLC.

### 6.4. Статусы для View — согласованная семантика, **новый enum пока не утверждён**

| Отображаемая причина | Смысл |
| --- | --- |
| `Connected` | Успешно поступают актуальные данные |
| `Connecting` | Идёт подключение/восстановление связи |
| `Disconnected` | Обмен потерян |
| `NoData` | Первый успешный snapshot ещё не получен |
| `BadConfig` | Неверная конфигурация/карта |
| `Error` | Внутренний отказ Core |

View должна показывать **первопричинную проблему**. `BadConfig` и `Error` нельзя автоматически маскировать под `Disconnected` или `NoData`. Детализированное логирование добавляется отдельным этапом. Правила вычисления итогового отображаемого состояния, когда одновременно актуальны разные факты (например, Connecting + NoData), и точные имена/сигнатуры публичного API ещё не согласованы. Не придумывать их при реализации.

## 7. Восстановление и отказ

- Потеря связи с PLC — штатное эксплуатационное состояние; Transport выполняет reconnect в рамках работающего Core.
- Client принимает статусы, не запускает параллельные reconnect и **не перезапускает Core** самостоятельно.
- Полный автоматический перезапуск экземпляра Core после внутреннего `Error` не считать реализованным: текущий `CoreLinkCore` запрещает повторный успешный `Start` того же экземпляра. Если когда-либо потребуется такой сценарий, его контракт уточняется отдельно.
- Не игнорировать неуспешный результат `ICore.Stop()`: результат остановки и фактический lifecycle Client должны быть согласованы.

## 8. Read/Write

Пользовательское требование: Client обеспечивает одиночные и блочные операции Read/Write по цепочке `View → Client → ICore → Core → Transport → PLC`. Одно соединение и существующий `ModbusRequestDispatcher` остаются в Transport. Второй диспетчер в Core или Client не создавать.

На дату документа `ICore` **не содержит** методов Read/Write. Не добавлять их без отдельного утверждения параметров, результатов, ошибок, cancellation и публичного API. Не заявлять несуществующую операцию реализованной.

## 9. Текущий статус реализации

**Реализовано:** `CoreLinkClient(IMapProvider, ICore)`, `Start(mapId)`, `Stop()`, `State`, `CoreMap`, создание `float[]`; `ICore.Start/Stop/GetSnapshot/StatusChanged`; C# Adapter, Core, Transport.

**Ещё не реализовано:** интеграция `ICore.GetSnapshot` в Client; управление Rx из Client; публичный интерфейс статусов View; Read/Write через ICore; завершённый контракт конкурентного взаимодействия Rx/Client. TestHost пока получает snapshot напрямую через адаптер.

**Известное несоответствие:** Client позволяет войти в `Start` после `Stopped`, тогда как текущий Core запрещает повторный Start того же экземпляра после успешного запуска. Не менять поведение без отдельного согласования lifecycle. `Client.Stop` сейчас не проверяет возвращённый статус Core.

## 10. Граница следующего шага

Сначала согласовать минимальный API передачи snapshot и статусов между Client и Rx, а также корректное время жизни буфера и порядок Stop. Затем доработать существующий `CoreLink.Client` и проверить путь через TestHost. Только после этого внедрять Rx в отдельном шаге.

**В текущий этап не входят:** Rust/FFI, OPC UA, переработка Transport, изменение карты v2, автоматический restart Core, новые `ICore` Read/Write без утверждения контракта.

Соблюдать правило `PROMT.md`: один файл за шаг, минимальный diff, код только по прямому запросу и после human review.
