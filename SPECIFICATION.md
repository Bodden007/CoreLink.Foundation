# CoreLink.Foundation — техническая спецификация

**Редакция:** 12.11.2026  
**Статус документа:** описание архитектуры и текущих контрактов с явным разделением **default branch GitHub** и **локально испытанных расширений**. Документ не является доказательством внедрения отсутствующих в ветке методов.

## 1. Назначение и технологическая основа

## Актуальный контракт выбора реализации ядра (13.11.2026)

**Инвариант:** `CoreLink.Client` зависит от `ICore`, а не от конкретной реализации ядра. `ICore` определён в `CoreLink.Contracts`. Конкретный адаптер выбирается на внешней точке композиции приложения и передаётся в конструктор `CoreLinkClient(ICore core)`. Это намеренное архитектурное решение, а не утечка внутренней реализации.

- Сегодня реализация `ICore` — `CoreLink.Adapter.CSharp.CSharpCoreAdapter`, который использует `CoreLink.Core` и `CoreLink.Transport`.
- Будущая реализация на Rust может быть подключена через другой адаптер `ICore` с сохранением публичного API Client, **если** выполняет тот же контракт. Rust/FFI-адаптер пока не считается реализованным.
- `CoreLink.Client` не должен создавать `CSharpCoreAdapter` самостоятельно, добавлять к нему прямую зависимость или определять платформенную реализацию ядра. Не скрывать выбор реализации внутри Client.
- Приложение работает с технологическими данными через `CoreLink.Client` и `CoreLink.Contracts`; точка композиции приложения дополнительно знает выбранный адаптер только для его создания. Это не означает, что ViewModel или UI должны вызывать методы адаптера.
- При поставке готовых DLL необходимы все транзитивные managed-зависимости выбранной реализации. Наличие `Adapter.CSharp.dll` в комплекте поставки не делает методы адаптера публичным прикладным API.
- Контракты и карты доступны извне: приложение составляет `CoreLinkMap` и вызывает `Start(CoreLinkMap)`. `ValueId` определяется позицией в карте, не адресом Modbus.
- Текущие методы записи: `WriteWordAsync`, `WriteFloatAsync`, `WriteBatchAsync`; интеграционное тестирование и промышленное подтверждение этих путей следует оценивать отдельно от наличия методов.
- Отдельная сборка managed DLL не тождественна NativeAOT-публикации приложения или созданию native-библиотеки Rust.


CoreLink.Foundation — инфраструктура обмена данными PLC для .NET 10. Текущий транспорт: Modbus TCP, NModbus 3.0.83. Область применения — приложения, которым нужны регулярная телеметрия, адресное чтение параметров, управляемое состояние связи и Rx-публикация изменений.

Основные инженерные приоритеты: надёжность, детерминированные статусы, слабая связанность, тестируемость, минимальная дополнительная инфраструктура. NativeAOT — целевое ограничение, **не** подтверждённый полный publish решения.

## 2. Компоненты и ответственность

```text
UI / Avalonia
      |
CoreLink.Client ───── CoreLink.Rx
      |                 |
     ICore        snapshot через Client
      |
CoreLink.Adapter.CSharp
      |
CoreLink.Core
      |
CoreLink.Transport
      |
Modbus TCP → PLC
```

| Проект | Ответственность | Не должен делать |
| --- | --- | --- |
| Contracts | API, карты, статусы | TCP и UI |
| Maps | физическая карта, Core v3 и managed Rx-карта | PLC I/O |
| Client | публичная точка, lifecycle, буферы, Rx | собственный Modbus polling |
| Adapter.CSharp | реализация интерфейса ICore над Core | самостоятельные карты и polling |
| Core | декодирование Word/Float32, snapshot, адресные запросы | Rx и UI |
| Transport | TCP, NModbus, Dispatcher, polling, timeout, reconnect | единицы измерения и UI |
| Rx | публикация готовых скаляров и обозначений | TCP, Modbus-адреса, reconnect |
| Client.TestHost | тесты взаимодействия | production-контракт |
| Внешний PlcSimulator | Modbus-сервер для испытаний | часть сборки основного решения |

**Одна TCP-сессия и один Dispatcher на транспортную сессию** для штатного polling и операций, которые проходят через CoreLink. Сторонний диагностический тестовый клиент в стресс-тесте этому требованию не эквивалентен.

## 3. Контракты и жизненный цикл

### 3.1 Реально прочитанный default branch на 11.11.2026

`ICore`: `Start(CoreMap)`, `Stop()`, `GetSnapshot(float*, int)`, `ReadAsync(IReadOnlyList<int>)`, событие `StatusChanged`.

`CoreLinkClient`: `Start(CoreLinkMap map)`, `GetSnapshot(out ReadOnlyMemory<float>)`, `ReadAsync(IReadOnlyList<int>)`, `StopAsync()`, `Stop()`, свойства `State`, `CoreMap`, `Values`, `Statuses`, метод `ObserveValue(int valueId)`.

`CoreStatus`, `CoreLinkState`, `SnapshotStatus` решают разные задачи. Возвращаемый snapshot — **копия в повторно используемый буфер Client**, а не долговременный immutable-array. Повторный Start после Stopped на том же Client не предусмотрен. Rx завершается прежде Core; пользовательский обработчик Rx не должен синхронно блокировать Stop.

### 3.2 Реализованный и локально испытанный Read API

```csharp
Task<CoreReadResult> ReadAsync(IReadOnlyList<int> valueIds);
```

В локальной реализации метод проведён через `Client → ICore → Adapter.CSharp → Core → Transport → Dispatcher → FC04`. Он **не** заменяет `GetSnapshot`, не изменяет snapshot и не публикует Rx напрямую.

`CoreReadResult`: `CoreReadStatus Status`, `float[]? Values`, признак `Ok`; статусы: `Ok`, `Disconnected`, `Timeout`, `Failed`, `BadConfig`, `Stopped`. При `Ok` значения соответствуют порядку входных ValueId; при неуспехе `Values=null`. Пустой, отрицательный и выходящий за карту ValueId — `BadConfig`. После Stop — `Stopped`.

Запросы по определению карты получают физический диапазон: Word — 1 регистр, Float32 — 2. Соседние диапазоны объединяются до Modbus-лимита 125 регистров, разрозненные читаются отдельно. Дублирование ValueId сохраняет дублирование результата. В этой версии запрос идёт по FC04 **Input Registers**, не FC03.

**Статус внедрения:** метод присутствует в текущей ветке GitHub; успешно собран и протестирован пользователем локально 11.11.2026.

### 3.3 Запись — открытая задача

Во внутренней `ModbusTransportSession` доступны `WriteSingleRegisterAsync` (FC06) и `WriteMultipleRegistersAsync` (FC16), и Dispatcher имеет очередь записи. **Историческая фиксация (11.11.2026): публичного Write API через ICore/Client на момент документации нет**.

Требуемый будущий путь: `Client → ICore → Core → Transport → Dispatcher`; единый transport/lifecycle и статусы, проверка адресов/типов и данных до постановки запроса в очередь. Диагностический FC03/FC06/FC16 в TestHost использует **отдельный TCP-клиент**; его успех не подтверждает арбитраж Write в CoreLink.

## 4. Polling, Dispatcher и Rx

- Polling: последовательный FC03 Holding Registers или FC04 Input Registers по `PollFunctionCode` из карты с интервалом `PollIntervalMs`. Циклы не должны бесконечно накапливаться.
- Dispatcher: приоритетная запись, затем штатный polling, затем адресный Read; в коде предусмотрена защита polling от полного голодания при потоке Write. Приоритет записи при общей сессии требует интеграционного теста.
- Rx: отдельный `RxIntervalMs` и готовый snapshot через Client. Значение публикуется, если изменилось число или отображаемая единица. Hot stream, без гарантированного replay.
- Snapshot: пока нет первого успеха — `NoData`; при потере актуальности — `Disconnected`; **не** выдавать старый массив как новые данные с успешным статусом.
- Никакого второго Modbus polling в Client или Rx.

## 5. Карта и типы

`ValueId == index` в `RegisterMap`. Не равен Modbus-адресу.

`CoreMap` binary v3: Little Endian; заголовок 34 байта; запись — `ushort Address` и `byte Type` (3 байта). `BufferLength` — число декодированных значений.

Подтверждённые типы: `Word`, `Float` (IEEE 754 Float32 из двух 16-битных регистров). Порядок слов/байтов задаётся картой; в испытаниях проверен текущий порядок и контрольные значения, **не все перестановки**.

Тестовая карта: 9 значений; `Measurme` — `ValueId=8`, физический адрес 0. Системы единиц 1 (UA), 2 (EU) зарегистрированы в карте. `0` — пустое обозначение; неизвестный/некорректный ID — `—` плюс диагностика. Rx не пересчитывает числовые значения. Новые положительные ID должны регистрироваться в карте, а не зашиваться в алгоритм Rx.

## 6. Ошибки и таймауты

Статусы Modbus Transport различают `Ok`, `Disconnected`, `ConnectTimeout`, `RequestTimeout`, `RequestFailed`, `Cancelled`, `Faulted`. Нормальная недоступность PLC не должна превращаться в необработанное исключение на публичной границе.

Если NModbus Task не отвечает за `RequestTimeoutMs`, Transport закрывает соответствующий TCP-сокет и ожидает физического завершения старой задачи до допуска новой операции. Отдельная диагностика отмечает:
- `RequestStartedCount` — начатые физические запросы;
- `RequestCompletedCount` — **в локальной исправленной версии** все завершённые физические запросы, включая ошибки;
- `HungRequestCount` — число превышений таймаута;
- `RecoveredRequestCount` — число старых запросов, завершившихся после принудительного закрытия сокета. **Это не число reconnect.**

Конкурентные диагностические поля не являются атомарным согласованным snapshot. Продолжительность Stop при активном отказе может быть больше миллисекунд.

Для диагностики использовать тестовый адрес `127.0.0.1:1502`, UnitId 1. Запись тестировать исключительно на эмуляторе.

| --- | --- |
| Build решения (8 проектов net10.0) | Успешно |

Тест не подтверждает latency, безопасность, атомарность отдельных пользовательских сценариев и арбитраж на настоящем PLC.

## 10. Проверенное состояние GitHub и уточнения — 11.11.2026

В текущей ветке **реально находятся**: `ICore.ReadAsync`, `CoreLinkClient.ReadAsync`, `CoreMapLayout.Version=3`, `HeaderSize=34`, `PollFunctionCode` и маршрутизация polling FC03/FC04 в Dispatcher. Значение `PollFunctionCode` передаётся в бинарном заголовке после `PollIntervalMs`. В `ConnectionMap` сейчас задан FC03.

**Разграничение API:** `PollFunctionCode` задаёт **функцию polling**. `ReadAsync(ValueIds)` в Core по-прежнему вызывает `session.ReadSingleAsync(start,count)` без выбора функции; при текущем значении по умолчанию это FC04. Прямой публичный выбор FC03/FC04 и публичный Write ещё не реализованы. Внутренние FC06/FC16 в Transport не являются пользовательским API.

**Локальные отказовые испытания, 60 секунд:** FC04 polling — Snapshot 81/120, ReadAsync 59/66, 186/186 запросов Transport завершено, 10/10 зависших I/O учтено, Stop 3,2 мс. FC03 polling после переноса диагностических записей в HR20–23 — Snapshot 67/120, ReadAsync 49/58, 154/154 запросов завершено, 10/10 зависших I/O учтено, Stop 4,1 мс. Оба прогона — `INVARIANTS PASSED` (0 ошибок тестовых проверок). Неудачные вызовы происходили во время намеренных OFFLINE/HANG. Эти числа не подтверждают промышленную надёжность и не являются тестами CI.

**Исправленный тестовый конфликт:** прежде диагностический FC06 записывал HR0, в то время как FC03 polling интерпретировал HR0 как `Measurme`; появлялись ошибки неизвестного значения. Тестовые регистры перенесены в HR20–23 внешнего симулятора, технологические HR0–16 не изменяются диагностическими записями. В последнем журнале ошибок `Unknown Measurme` нет.

**Утверждённый ближайший объём:** объединить тесты чтения и polling в один автоматически выполняемый сценарий для FC03/FC04 с OFFLINE, HANG, RECOVERY и Stop, без ручной смены конфигурации. **Публичный Write и тесты записи отложены** до завершения чтения; найденные дефекты устранять точечно. Диагностический NModbus-клиент с отдельным TCP не засчитывать как проверку прямого CoreLink API.


## 12. Адресная Rx-подписка: API и состояние реализации на 12.11.2026

**Исходник GitHub:** `CoreLink.Client/CoreLinkClient.cs` содержит `IObservable<RxValue> ObserveValue(int valueId)`. Внутренний `CoreLinkRx.Values` уже является горячим защищённым потоком; новый метод применяет `System.Reactive.Linq.Where(value => value.ValueId == valueId)`. Полный `RxValue` = `(ValueId, Name, Value, Unit)`, где `Unit` — обозначение единицы (не численное преобразование).

**Согласованный публичный контракт:** адресная подписка по `ValueId`; один цикл Rx и одинаковая рассылка любому числу независимых подписчиков; каждому принадлежит свой `IDisposable`; никаких replay, дополнительных snapshot или новых транспортных запросов. Публикация только при изменении значения или обозначения единицы. `Statuses` остаётся отдельной необязательной подпиской; не интегрировать состояние связи в `RxValue`. `CoreLinkClient` создаётся один на сессию; `Start(mapId)` выполняется до подписок, `StopAsync()` — при остановке приложения. При необходимости UI-обновления ViewModel использует `ObserveOn(RxSchedulers.MainThreadScheduler)`.

**Реальное поведение ошибок:** `ObserveValue` не выбрасывает исключения наружу при неработающем Client/Rx, неверном `ValueId` или исключении во время создания потока, а возвращает `Observable.Empty<RxValue>()`. `Empty` немедленно сигнализирует `OnCompleted` своему подписчику. Логирование таких отказов **не реализовано**: соответствующие `TODO` в методе остаются обязательной будущей работой. Не маскировать эту диагностическую недоработку утверждением о готовом production logging.

**Различать согласованное и текущее:** правило «штатный Stop не вызывает `OnCompleted`/`OnError`» согласовано, **но в репозитории пока не реализовано**: `CoreLinkRx.DisposeCoreAsync()` вызывает `OnCompleted` у `_values` и `_statuses`. Это известное расхождение и отдельная задача; не править попутно документацию/код других подсистем.

**NativeAOT:** оператор Rx `Where` сам по себе не требует динамической генерации кода, но окончательная AOT-совместимость нового API подтверждается только NativeAOT publish и исполнением подписки в smoke test. Полная проверка решения не заявлена.

**Правило следующих сессий:** не начинать повторный опрос пользователя по уже утверждённым решениям Rx и не заменять существующий механизм иной архитектурой; сначала читать текущий код и эти нормативные документы. Любые оставшиеся правки делать минимально, только по отдельному запросу.
