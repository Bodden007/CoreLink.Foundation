# CoreLink.Foundation — промпт реализации Read/Write регистров

**Дата:** 11.11.2026  
**Статус:** согласованная концепция Read; Write — рамки и существующие механизмы, детали публичного контракта уточняются при реализации.  
**Связанные документы:** [PROMT.md](PROMT.md), [CLIENT_CONTRACTS.md](CLIENT_CONTRACTS.md), [MAP_PROMT.md](MAP_PROMT.md).

## 1. Задача и принцип

Добавить прямое чтение и запись регистров из приложения через **существующую цепочку**:

```text
View / ViewModel → CoreLink.Client → ICore → CoreLink.Adapter.CSharp
                 → CoreLink.Core → CoreLink.Transport → Dispatcher → NModbus → PLC
```

Ориентир для простоты — проверенный прикладной подход **Nitrogen.Legacy**, особенно [PressureSetControlViewModel.cs](https://github.com/Bodden007/Nitrogen.Legacy/blob/master/Nitrogen/Views/Settings/PressureSet/PressureSetControlViewModel.cs): ViewModel по необходимости вызывает асинхронное одиночное или блочное чтение; возвращённые регистры сразу используются для отображения. Запись выполняется обычными NModbus-командами одиночного/блочного формата. Не переносить старую работу с физическими адресами в новую ViewModel.

**Главный принцип: не строить новую подсистему вокруг штатных операций NModbus.** Минимальное расширение существующих компонентов и минимальный diff.

## 2. Прямое чтение — утверждённый контракт

1. ViewModel инициирует **один асинхронный вызов** по потребности экрана; UI-поток не блокируется.
2. Снаружи используется **логический `ValueId`**, а не адрес PLC. `ValueId == index` в карте. Адрес и тип регистра определяет Core по текущей карте.
3. Допускается чтение **одного значения** или **набора значений**. В зависимости от требуемых физических адресов это может быть одиночный запрос, один непрерывный блочный запрос либо несколько запросов. Не создавать специальный механизм автоматической консолидации/планирования.
4. NModbus читает непрерывный диапазон физическими регистрами. `Word` занимает один регистр, `Float32` — два. Использовать существующую трактовку порядка слов/байтов карты; возвращать внешнему коду декодированные **`float`** в порядке запрошенных `ValueId`.
5. На успехе ViewModel сразу получает значения и отображает их; прямой Read **не изменяет** основной snapshot и **не публикует** значения в Rx/HMI-поток штатного polling.
6. **Один общий итоговый статус** для вызова: успех, ошибка запроса, потеря связи и т. п. Не делать статусы для каждого регистра.
7. **Любая ошибка Modbus завершает текущий Read**; не объявлять частично прочитанные данные успешным результатом. Не выполнять автоматических повторов неудачного чтения. Новый Read инициирует приложение.
8. Операции идут через **существующий Dispatcher и одну TCP-сессию**. Никаких дополнительных worker, собственных сетевых клиентов, транзакционных очередей или специальной эксклюзивной блокировки всей группы. Обычный polling продолжает жить по действующей схеме диспетчеризации; записи обслуживаются с существующим приоритетом. Не вводить отдельное правило «остановить polling до завершения всего вызова».
9. Корректная организация последовательности вызовов ViewModel — ответственность приложения. Не строить отдельную подсистему для гипотетических гонок двух ViewModel.
10. На `Stop` операция не должна препятствовать штатной остановке Client/Core/Transport; опираться на существующие cancellation/timeout/lifecycle гарантии. Внешняя граница возвращает контролируемый статус.

**Уточнение области:** текущий физический путь чтения Transport — Modbus **FC04 (Input Registers)**. Не обещать чтение Holding Registers без отдельного согласования и реализации.

## 3. Запись — рамки задачи

1. Предоставить приложению прямые **асинхронные** операции записи: одиночный регистр и непрерывный блок, когда они нужны ViewModel.
2. Использовать уже существующие `WriteSingleRegisterAsync` и `WriteMultipleRegistersAsync` в Transport/Dispatcher/NModbus, без второго канала обмена.
3. Не переносить произвольные физические адреса и декодирование в UI. Логическую адресацию и преобразование значений выполнять на соответствующей границе Core/карты; **конкретные публичные сигнатуры и модель карты для writable-регистров не считать утверждёнными**, если текущая карта их не описывает.
4. Возвращать единый статус результата записи; штатные ошибки Modbus не превращать в исключения на внешней границе. Не добавлять автоматические повторы, скрытые повторные записи или проверочное чтение без прямого требования.
5. Пример Nitrogen.Legacy с записью блока из восьми `ushort` и последующим одиночным флагом применения параметров — **пример двух явно вызванных операций ViewModel**, а не обязательная новая универсальная транзакция CoreLink.

## 4. Границы компонентов и запреты

- **Client** — публичное API, управление сессией и возврат результата; не выполняет Modbus I/O, не ищет адреса и не создаёт polling.
- **ICore / Adapter** — минимальное расширение контракта и маршрутизация операции.
- **Core** — `ValueId` → регистр(ы), преобразование `ushort` ↔ значения, контроль конфигурации; прямой Read не обновляет snapshot.
- **Transport / Dispatcher** — сохраняют одну TCP-сессию, существующие приоритеты, сериализацию Modbus-запросов, request timeout, reconnect и lifecycle. Изменять их только при обнаружении конкретной необходимости.
- **Rx** — не трогать ради Read/Write.
- Не менять бинарную карту v2 «на всякий случай», не вводить новый диспетчер, команды-обёртки ради будущего, фоновый polling Client, сложную оркестрацию групповых операций.
- Не полагаться на то, что `Task` автоматически гарантирует отсутствие блокировок или безопасность Stop: проверять реальный путь завершения.

## 5. Практический порядок реализации

1. Перед кодом сверить актуальные исходники `ICore`, адаптера, Core, `ModbusTransportSession`, Dispatcher, ConnectionManager и карты.
2. Сначала добавить **минимальный Read**, проверить одиночное и блочное чтение, декодирование `Word`/`Float32`, отсутствие влияния на snapshot и Rx.
3. Проверить ошибки, отсутствие повторов, нормальный polling во время прямых запросов и штатный Stop.
4. Затем реализовать **минимальный Write**, не придумывая формат writable-карты без подтверждения.
5. Сборка, испытания на `CoreLink.PlcSimulator`/тестовом PLC и проверка отказов. NativeAOT считается требованием, а не автоматически доказанным результатом.
6. Работать по [PROMT.md](PROMT.md): без кода до команды разработчика, минимальные изменения, по одному полному файлу за шаг; не менять границы архитектуры без согласования.

## 6. Критерий готовности

ViewModel вызывает требуемое асинхронное чтение/запись через Client, получает значения либо **общий статус ошибки**, при этом продолжают корректно работать существующие polling, Rx, snapshot, приоритеты запросов и остановка сессии. Нет новой сетевой инфраструктуры и нет усложнения ради гипотетических сценариев.

**Важно:** данный документ — **задание на реализацию**, а не утверждение, что публичные Read/Write уже реализованы. Для Write детали контракта, которых нет в нынешней карте, нельзя выдумывать молча.
