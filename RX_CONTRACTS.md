# CoreLink.Rx — архитектурный контракт и инженерный промт

**Репозиторий:** https://github.com/Bodden007/CoreLink.Foundation  
**Дата:** 10.11.2026  
**Статус:** согласованная концепция; реализация CoreLink.Rx на момент документа отсутствует.  
**Связанные документы:** [PROMT.md](PROMT.md), [CLIENT_CONTRACTS.md](CLIENT_CONTRACTS.md).

> Архитектурный контракт для проектирования и реализации реактивной инфраструктуры CoreLink. Не выдавать утверждённую концепцию за уже существующий код. Архитектуру и публичные сигнатуры утверждает разработчик.

## 1. Назначение

`CoreLink.Rx` — инфраструктура реактивной обработки и распространения **готовых числовых значений** CoreLink. Rx получает snapshot **только через CoreLink.Client**, выполняет прикладные преобразования и оповещает подписчиков готовыми значениями.

**Client — единая публичная точка интеграции приложения с инфраструктурой.** Client создаёт, запускает, останавливает и освобождает Rx. View/ViewModel не создают Rx и не взаимодействуют с Core или Transport напрямую.

```text
PLC
  ↓
CoreLink.Transport (независимый polling из карты)
  ↓ ushort[]
CoreLink.Core (декодирование Word/Float32; собственный snapshot)
  ↑↓ ICore.GetSnapshot
CoreLink.Client (собственный float[]; lifecycle, статусы)
  ↑↓ запрос и результат
CoreLink.Rx (свой заранее выделенный float[], преобразования, hot stream)
  ↓ готовые значения / отображаемые статусы
Подписчики View/ViewModel (только отображение)
```

## 2. Утверждённый цикл Rx

**Таймер/задержка Rx — 500 мс.** Это интервал **потребительского** цикла, а не `PollIntervalMs` Transport.

1. Rx ожидает 500 мс после завершения предыдущего цикла (при первом запуске порядок первого запроса может определяться реализацией).
2. Rx сообщает Client о готовности принять данные / инициирует запрос.
3. Client синхронно вызывает `ICore.GetSnapshot` для заполнения **собственного** Client-буфера.
4. Client возвращает в Rx результат: при `Ok` — данные; иначе — `SnapshotStatus` без выдачи прежнего буфера как свежего.
5. Rx при `Ok` копирует значения в **свой заранее выделенный** буфер, выполняет прикладную обработку.
6. Rx публикует готовые значения подписчикам.
7. Цикл считается завершённым; следующая итерация может начаться только после его завершения и выдерживания 500 мс.

```text
Delay 500ms → Ready → Client.GetSnapshot → [Ok?]
                                          ├─ Yes → Copy → Process → Publish
                                          └─ No  → Retain last values + status
                               → cycle complete → Delay 500ms → ...
```

**Инвариант:** одновременно не существует двух активных циклов Rx, использующих Client-буфер. Новый запрос не создаётся, пока предыдущий цикл Rx не закончен. Тики не накапливаются в очереди. Для этого предпочтителен простой последовательный цикл с задержкой **после** завершения работы; конкретную реализацию таймера/планировщика согласовать до написания кода.

Rx не запрашивает следующий snapshot из обработчика подписчика. **Подписчики не подтверждают чтение (никаких ACK).**

## 3. Буферы и ownership

Существуют три независимо принадлежащих массива:

| Буфер | Владелец | Роль |
| --- | --- | --- |
| Core snapshot | Core | Последнее согласованное техническое состояние после декодирования |
| Client `float[]` | Client | Передача последнего snapshot через синхронный `ICore.GetSnapshot` |
| Rx `float[]` | Rx | Последние значения и прикладная обработка |

- Client и Rx создают свои массивы **один раз при старте сессии**, размер согласован с `CoreMap.BufferLength`. Не выделять новый рабочий `float[]` на каждом цикле.
- `ICore.GetSnapshot` работает только с Client-буфером: Client временно закрепляет его через `fixed`, Core не сохраняет указатель.
- Rx **не передаёт исходный Client-буфер подписчикам**.
- Rx копирует значения Client-буфера в свой буфер при `SnapshotStatus.Ok`. После завершения копирования Client-буфер может быть повторно использован, но по выбранной концепции следующий запрос выполняется только после полного цикла Rx.
- **Ни Client-, ни Rx-рабочий изменяемый массив не отдавать подписчикам для асинхронного использования.** Подписчики получают подготовленные значения/стабильные результаты обработки; их конкретный контракт будет утверждён отдельно.
- Цикл Rx завершается до следующего запроса; для обычного последовательного обмена Client ↔ Rx дополнительные ACK и блокировки подписчиков не требуются.
- Исключить гонку Stop с запросом/copy/process, прежде чем освобождать массивы. Нельзя освобождать ресурсы, пока активный цикл использует их.

**Нулевая аллокация в горячем цикле — цель для рабочих буферов**, но не заявлять доказанную полную безаллокционность Rx без проверки публикации, операторов и подписчиков.

## 4. Обработка и границы

**Core уже декодирует Modbus WORD и Float32, учитывает order, публикует согласованный `float[]`.** Rx не повторяет протокольное декодирование и не знает адресов, Modbus function codes, TCP, reconnect или ICore.

**Rx отвечает за прикладную обработку после получения готовых значений:** преобразование, фильтрацию и подготовку значений для подписчиков — только те операции, которые будут явно определены предметной задачей. Не добавлять произвольные фильтры, масштабирование, вычисления или Units API заранее.

**View/ViewModel только отображают готовые значения** и статусы, не обрабатывают исходные массивы и не управляют циклом Rx.

## 5. Потеря данных, качество и статусы

- При `Ok`: Rx обновляет собственный буфер, обрабатывает данные, публикует готовые значения.
- При `NoData` до первого успешного snapshot: **валидных последних значений ещё нет**. Нулевой инициализированный буфер нельзя считать показаниями PLC.
- При `Disconnected` или `NoData` после успешного snapshot: **последние успешно принятые значения в Rx сохраняются**, но должны считаться устаревшими/неактуальными; не публиковать их как новые свежие измерения.
- При повторном `Ok`: Rx обновляет свой буфер и возвращается к публикации свежих значений.
- Ошибки/статусы `BadBuffer`, `Stopped` не считать измерениями.
- Client принимает `CoreStatus` и `SnapshotStatus`; внешний набор первопричинных статусов для View согласован концептуально: `Connected`, `Connecting`, `Disconnected`, `NoData`, `BadConfig`, `Error`. Существующих типов `CoreStatus`, `SnapshotStatus`, `CoreLinkState` не смешивать.
- `BadConfig` и `Error` не маскировать `Disconnected`. Расширенная диагностика/логирование — будущий отдельный этап.
- Механизм объединения и публикации View-статусов (через Client и/или поток Rx), приоритет одновременных состояний и точные имена enum **пока не утверждены**. Не придумывать контракт молча.

## 6. Подписчики и UI

- Один экземпляр Rx обслуживает множество подписчиков через **общий hot observable stream**.
- Основные подписчики создаются/подключаются при запуске приложения.
- Дополнительный экран подписывается при открытии и вызывает `Dispose()` подписки при закрытии.
- Закрытие экрана не останавливает Rx, Core и Transport, остальные подписчики продолжают работать.
- Новая подписка ожидает **следующую публикацию**. Replay/BehaviorSubject для последнего значения без отдельного требования не вводить.
- Подписчики только отображают подготовленные значения. Никаких ACK/подтверждений прочтения, очередей подтверждений и ожидания каждого подписчика.
- `ObserveOn`/асинхронная доставка могут означать, что UI ещё не обработал значение к моменту возврата из `OnNext`. Поэтому объект публикации не должен ссылаться на изменяемый рабочий буфер Rx, который будет перезаписан следующим циклом.
- Не считать вызов `OnNext` подтверждением завершения асинхронной обработки UI. Это **не требуется** по принятой концепции.

## 7. Lifecycle и остановка

- Rx создаётся и запускается владельцем `CoreLink.Client`, не из View.
- Rx не стартует Core/Transport самостоятельно и не инициирует PLC reconnect или Core restart.
- При остановке Client прекращает новые запросы Rx, завершает текущую итерацию/ожидает её безопасного окончания, освобождает Rx/подписки инфраструктуры, затем останавливает Core и освобождает Client-буфер.
- Закрытие одного экрана уничтожает только его подписки.
- Конкретный механизм cancellation и публичные сигнатуры Start/Stop/Dispose для Rx **не определены**: не изобретать их до согласования.
- Обработка ошибки внутри Rx не должна превращаться в неконтролируемый tight loop; после неуспешного результата повторяется обычный последовательный цикл с задержкой 500 мс, если владелец не остановил Rx.

## 8. Чего Rx принципиально не делает

- Не вызывает `ICore` и не работает с unsafe указателями.
- Не открывает TCP/Modbus, не читает физические регистры напрямую.
- Не декодирует WORD/Float32 и не парсит бинарную карту.
- Не управляет Core lifecycle и не перезапускает ядро.
- Не предоставляет отдельную физическую Read/Write очередь (эти команды идут через Client → Core → Transport).
- Не отдаёт рабочие буферы View, не ждёт ACK от подписчиков.
- Не делает собственные копии transport polling, не накапливает очередь устаревших snapshot.
- Не вводит generic message bus, DI-scanning, reflection, replay и иные абстракции «на будущее» без реального требования.

## 9. Границы реализации и проверка

**Confirmed (концепция):** последовательный цикл Rx с задержкой 500 мс после обработки, запрос через Client, буфер Rx создаётся при старте и переиспользуется, сохранение последних значений при потере связи, общий hot stream, Dispose подписок экранов, отсутствие ACK.

**Confirmed (существующий код):** `ICore.GetSnapshot(float*, int)`, `SnapshotStatus`, Core snapshot и клиентский буфер в CoreLink.Client. Сам Rx **ещё не реализован**.

**Unknown (только перед реализацией соответствующей части):** публичный API Client ↔ Rx, типы результата подписчикам, карта прикладных преобразований и Units, способ трансляции ошибок во View, отмена текущего цикла при Stop. Не маскировать эти вопросы новыми произвольными интерфейсами.

**Порядок работы:** изучить текущий код → согласовать API затрагиваемой границы → по явному запросу написать **полный файл в чате, по одному файлу за шаг** → build → целевой тест → human review → commit.

**Не менять на этапе Rx без отдельного решения:** `ICore`, бинарную карту v2, Transport/Dispatcher/Poller, механизмы reconnect, новые Read/Write API, Rust/FFI/OPC UA.
