# CoreLink.Rx — реализованный контракт и инженерные правила

**Актуализировано:** 12.11.2026  
**Статус:** Rx интегрирован с Client/Maps. Рабочий цикл и выбор обозначений проверены интеграционно; production-журналирование и третья зарегистрированная система не подтверждены.

## 1. Ответственность и данные

`CoreLink.Rx` обрабатывает **готовые `float`-значения**, полученные синхронно через `SnapshotReader` Client. Rx не обращается к `ICore` напрямую, не работает с указателями, TCP, Modbus-адресами, бинарной картой или reconnect.

Тип публикации: `RxValue(int ValueId, string Name, float Value, string? Unit)`. `ValueId == index` в `RegisterMap`/snapshot. Rx **не пересчитывает** psi/bar/MPa, а только выбирает текст обозначения из карты.

## 2. Актуальная инициализация

`CoreLinkRx(SnapshotReader snapshotReader, IReadOnlyList<RxValueDefinition> definitions, int? unitSystemValueId, IReadOnlyCollection<int> supportedUnitSystemIds, int intervalMs)`.

`RxValueDefinition` хранит имя и `IReadOnlyDictionary<int,string> Units`. Допустимые системы передаются отдельно: **наличие единицы у конкретного параметра не определяет существование всей системы**. Rx проверяет конфигурацию перед запуском, а не использует прошитое сравнение `1 or 2` в рабочем цикле.

Rx предоставляет `Values`, `Statuses`, `HasData`, `IsFaulted`, `LastError`, `Start()`, `StopAsync()`, `DisposeAsync()`. Внешний владелец — Client.

## 3. Рабочий цикл и память

1. Rx получает `SnapshotStatus` и `ReadOnlyMemory<float>` через Client.
2. При `Ok` проверяет длину, читает `Measurme`, сравнивает новое значение и выбранное обозначение каждого параметра с предыдущим.
3. Публикует `RxValue` **только когда изменилось число или обозначение** (первый успешный snapshot публикует все значения).
4. После цикла выполняет задержку `RxIntervalMs` (текущая карта — 500 мс). Очередь тиков, ACK от UI, отдельный transport polling не используются.

Rx хранит свой рабочий `float[]`. `RxValue` копирует скаляр, имя и строку: подписчик не получает ссылку на изменяемый массив. Основные подписки создаются приложением; подписки экранов освобождаются при закрытии. Общий поток — **hot**, обязательного replay для нового подписчика нет. Ошибка одного подписчика должна быть диагностирована и изолирована от остальных.

## 4. Выбор системы единиц

`Measurme` — точное имя регистра; `UnitSystemValueId` определён по его позиции в карте. Отсутствует регистр — default ID 1 (он обязан быть зарегистрирован). Неверный ID не подменять на 1.

| Measurme | Unit | Ошибка |
| --- | --- | --- |
| 0 | Пустая строка | Нет |
| Зарегистрированный положительный ID с записью единицы | Символ из `definition.Units` | Нет |
| Зарегистрированный ID без записи для данного параметра | Пустая строка | Нет |
| Неизвестный/нецелый/недопустимый ID | `—` (для всех параметров) | Диагностика |
| После ошибки пришёл 0 или известный ID | Пустая или штатная единица | Сообщение восстановления |

Неизвестный ID не сбрасывает число. При смене неизвестного ID на другой неизвестный прочерк не изменяется — не рассылать все параметры только из-за такой смены. Сам регистр `Measurme` публикуется при изменении его числового значения.

`ReportUnitError` подавляет повторы **той же причины**; `ClearUnitError` отмечает восстановление. Диагностика сейчас через `Trace.TraceError` и `Trace.TraceInformation`. **Не подтверждены** её сбор/сохранение через конкретный `TraceListener`, запись в файл и проверка одноразовости сообщений реальным журналом.

## 5. Качество snapshot и отсутствие данных

- `NoData` до первого успешного snapshot не означает реальные нули; измерения не публикуются.
- При `Disconnected`/неуспешном snapshot последние значения не публикуются как свежие и не заменяются нулями; отображающий слой обязан учитывать `SnapshotStatus`.
- При восстановлении `Ok` продолжается обычное сравнение новых значений/единиц.
- `BadBuffer` и `Stopped` — не данные измерений.
- Rx не выполняет принудительную смену единиц только по факту обрыва связи.

## 6. Lifecycle, диагностика и границы

Client запускает Rx после Core и останавливает/dispose Rx до Core. `StopAsync` и `DisposeAsync` рассчитаны на повторные/конкурентные вызовы; не блокировать этот путь из обработчиков подписок синхронными вызовами Client.Stop.

Ошибки внутри Rx локализуются и сохраняются в `LastError`; не выдавать `NoData` или `Disconnected` за внутренний `BadConfig/Error`. Исключения подписчиков не должны ломать общий поток.

Новые фильтры, масштабирование, расчёты, интерфейсные переводы, replay, новые status enum, message bus, DI/reflection, прямой PLC Read/Write, Rust/FFI — **не реализовывать без согласования**. Внутренние валидационные `ThrowIf...` в `RxValueDefinition` требуют отдельного аудита на соответствие правилу NO EXCEPTION PROPAGATION; не объявлять это исправленным без изменения кода.

## 7. Проверки и незакрытое

10.11.2026: подтверждены сборка .NET 10, работа реального Client + Rx на внешнем PLC Simulator, переключения `0/1/2/3/5/8/9`, восстановление символов, отсутствие лишних публикаций при неизменном обозначении, 121/121 запрос, 120 успешных snapshot, 0 ошибок snapshot, 488 Rx values, успешный Stop.

**Открыто:** тест **зарегистрированной** системы 3 (с новой записью `UnitEntry`), проверка `Trace`/восстановления через настроенный listener, production-логгер, анализ специальных нецелых значений, более широкие отказовые тесты после расширения карты. Это не препятствует признанию пройденных сценариев, но не позволяет заявлять полную промышленную готовность.

См. [PROMT.md](PROMT.md), [MAP_PROMT.md](MAP_PROMT.md), [CLIENT_CONTRACTS.md](CLIENT_CONTRACTS.md).

## 8. Независимость прямого Read/Write и результаты 11.11.2026

Реализованный в GitHub `CoreLinkClient.ReadAsync` отправляет прямой FC04-запрос через Dispatcher и **не генерирует RxValue сама**; Rx по-прежнему получает только готовый snapshot. В 60-секундном стабильном стрессе при одновременном polling/Read и внешней диагностической записи зарегистрировано 425 Rx value events и один успешный статус, нарушений инвариантов не обнаружено. В сценарии OFFLINE/HANG/RECOVERY зафиксировано 268 Rx value events и 6 status events; Rx возвращался к `Ok` после восстановления связи.

FC06/FC16 выполнялись независимым диагностическим TCP-клиентом, а не через публичный CoreLink: этих данных недостаточно, чтобы признать проверенным приоритет Write внутри Dispatcher. Прямой Read уже присутствует в текущей ветке GitHub; при работе с другими ветками сверять исходник.

## 9. Совместимость с polling FC03 и изоляция Measurme

Rx не зависит от Modbus FC: он получает декодированный snapshot через Client одинаково для FC03 и FC04 polling. `PollFunctionCode` задаётся в CoreMap v3, а не в Rx-проекции. В локальном испытании 11.11.2026 FC03 polling подтверждены штатные `Measurme=1`, восстановление `Rx STATUS: Ok` после OFFLINE/HANG и отсутствие повторяющейся ошибки неизвестной системы после переноса диагностической записи из HR0 в HR20–23. В последнем FC03 прогоне зарегистрировано 9 Rx value events и 6 status events; малое число value events само по себе не ошибка, поскольку исходные Holding Registers в симуляторе в основном постоянны и Rx публикует изменения, а не каждый snapshot.


## 10. Адресный публичный API и завершение — решение 12.11.2026

В `CoreLinkClient` реализован `ObserveValue(int valueId): IObservable<RxValue>`, фильтрующий **существующий** поток `CoreLinkRx.Values` по `ValueId`. Rx продолжает однократно обрабатывать каждый snapshot и публиковать изменение числа либо обозначения единицы. Несколько подписчиков одного значения получают одинаковые события; каждая ViewModel/окно освобождает свой `IDisposable`. Отдельные рабочие циклы, replay и принудительный snapshot на подписку **не допускаются**. `RxValue` сохраняет `ValueId`, `Name`, `Value`, `Unit`.

Статус качества snapshot **не входит** в индивидуальные значения: `CoreLinkClient.Statuses` остаётся независимым необязательным `IObservable<SnapshotStatus>?`. Если окно должно показывать состояние связи/свежести, оно отдельно подписывается на `Statuses`; потеря связи не публикуется как новое измерение. Контекст исполнения существующего Rx не перепроектировать; ViewModel при потребности использует `ObserveOn` для UI.

Некорректный `ValueId`, недоступный Client/Rx и ошибка формирования `ObserveValue` сейчас приводят к `Observable.Empty<RxValue>()`, без выброса исключений наружу. `Empty` завершает подписку через `OnCompleted` немедленно — это реальное свойство текущего API. В Client оставлены `TODO` для будущего централизованного логирования; не объявлять их реализованным журналированием.

**Зафиксированное, но ещё не реализованное правило Stop:** штатная остановка должна прекратить события без `OnCompleted`/`OnError`. На момент документации `CoreLinkRx.DisposeCoreAsync` по-прежнему вызывает `_values.OnCompleted()` и `_statuses.OnCompleted()`. Это явный пункт для отдельного минимального изменения и проверки. Прочие уже работающие механизмы Rx, включая защиту подписчиков, не переписывать.
